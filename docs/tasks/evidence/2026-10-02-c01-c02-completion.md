# C01、C02 库存与 Run 状态机收口

## 执行范围

沿用 Canonical Spec 与 Task，保存现有工作区修改。C01 对照当前生产者、消费者、持久化和目标运行态更新库存；C02 覆盖创建、投递、领取、提交、取消、重试、恢复与响应。其他父组的真实来源、客户端整体和发布验收分别保留。

## 当前发现与验证计划

当前 Controller 与 API Client/Desktop 使用 `runs`，旧 `jobs` HTTP 入口已移除。创建在数据库访问前拒绝旧合同，当前模式为 `V3`。领取前预算失败的两处 CAS、恢复取消/预算失败/耗尽/重新排队的四处 CAS 缺少模式条件，需补齐并验证读取后模式变更不会写入旧记录。

验证顺序：定向状态机及并发测试、Server 包级与类型/build、边界门禁、隔离 PostgreSQL 和实际 Worker、官方快更、目标 HTTP 与数据库不变性检查。

## C02 实施与断言

- 创建：`BacktestRunService` 在旧 outer contract 进入 lifecycle 前拒绝；严格请求 Schema 在数据库访问前解析。幂等创建只返回同一策略版本、配置与 key 的现行记录。目标重复请求返回同一 Run，无新行。
- 领取与提交：全部模式使用 `V3`；领取、成功、失败、取消确认和重试按状态与 attempt 原子更新。新增两处预算失败和四处恢复 CAS 的模式条件，防止读取后模式变更误写旧记录。
- 恢复：按职责拆出 `reconcileJob`，分页扫描与单条 Run 恢复分别负责；队列查询失败不会被当作缺失，取消仅在已确认队列缺失/终态后确认。预算无效与耗尽分别收敛为稳定错误码。
- 重试：手动重试核验冻结输入，基数与 attempt 单调递增；失败后离线重读产物，不重新调用在线 DSA。重复执行与晚到提交由 CAS 拦截。
- 消费面：API Client 当前 Run 响应严格解析；Desktop 的实际 Run/NAV 路径与 Controller 一致。旧 jobs 没有生产 HTTP 消费者，目标 GET/POST/详情均404。列表/单项冻结读取复用 C04；真实 Desktop NAV 创建、详情、重试复用 N4 未变化证据，不把这些结论扩展成 U01/U02 全量完成。

本轮仅修改 execution owner、queue reconciler、对应回归和隔离 PostgreSQL 验收接入；新增目标验收脚本。没有改 Schema、migration、依赖或镜像。隔离测试只操作带唯一身份的临时数据库/Redis，由已有 harness 清理；目标请求只有拒绝路径与已有记录的幂等创建。
