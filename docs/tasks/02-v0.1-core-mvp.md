# V0.1：核心 MVP 闭环

> 阶段目标：跑通真实持仓 → 行情 → 盈亏 → 风险 → 飞书 → AI 解释；完成 Screenshot Import 差异化链路。

- [x] T019：定义 Asset 领域模型
  - 涉及范围：定义 symbol、name、market、assetType、currency 及 A 股/ETF/基金/现金基本语义。
  - 完成条件：Domain 包导出唯一 Asset 类型；Server/Desktop/Mobile 不再自行定义重复 Asset。
  - 验证方式：类型检查并搜索重复模型；用股票、ETF、基金各一个 fixture 验证序列化。

- [x] T020：实现 Symbol Normalization
  - 涉及范围：统一 SH/SZ 等市场后缀、代码长度、ETF/股票识别和名称辅助匹配。
  - 完成条件：内部 symbol 固定为如 `600519.SH`、`000001.SZ`；非法代码返回明确错误。
  - 验证方式：单元测试覆盖沪市、深市、ETF、缺后缀、非法长度和未知市场。

- [x] T021：定义 Quote Contract
  - 涉及范围：统一实时价格、OHLC、昨收、成交量/额、marketTime、fetchedAt、provider、stale。
  - 完成条件：Quote Schema 在 packages/schemas 中版本化；所有行情适配输出都能通过校验。
  - 验证方式：使用 DSA 样例和 Mock 样例做 schema parse，错误字段必须失败。

- [x] T022：定义 Bar Contract
  - 涉及范围：统一 1d/1m Bar 的 OHLCV、amount、timestamp、provider 等字段。
  - 完成条件：Bar Schema 支持数组校验、按时间排序要求和 timeframe。
  - 验证方式：构造乱序、缺字段、非法 OHLC 数据，验证 schema/validator 行为。

- [x] T023：定义 Indicator Contract
  - 涉及范围：定义 indicator name、parameters、timeframe、marketTime、values、provider。
  - 完成条件：MA/MACD/RSI/ATR 能在同一结果结构中表示，且带参数和时间。
  - 验证方式：对四种指标各做一个契约测试。

- [x] T024：定义 ChipDistribution Contract
  - 涉及范围：定义 buckets、averageCost、mainPeak、profitRatio、range70、range90、concentration、engineVersion。
  - 完成条件：DSA 和未来 InStock 实现都可映射到同一结构。
  - 验证方式：用固定 fixture 验证 price bucket 权重、区间格式和可选字段。

- [x] T025：实现 DSA HTTP Client
  - 涉及范围：实现 base URL、timeout、retry、traceId、错误映射和响应日志脱敏。
  - 完成条件：所有 DSA 调用必须经过该 Client；业务层无裸 fetch/axios 指向 DSA。
  - 验证方式：停止 DSA、制造超时、返回 500，确认错误均转成统一错误。

- [x] T026：实现 Quote Adapter
  - 涉及范围：将 DSA 实时报价映射为内部 Quote，并补 symbol normalization、provider、时间字段。
  - 完成条件：Server 的 `market.getQuote()` 不暴露 DSA 原始结构。
  - 验证方式：查询 600519.SH 并与 DSA 原始响应核对价格与时间。

- [x] T027：实现 Bars Adapter
  - 涉及范围：将 DSA 日线和 1 分钟 K 线映射为 Bar[]，处理复权参数和时间排序。
  - 完成条件：支持 1d/1m；返回结果满足 Contract，空数据明确区分无交易和错误。
  - 验证方式：对同一股票分别查询 1d/1m，验证排序、数量和 OHLC。

- [x] T028：实现 Indicator Adapter
  - 涉及范围：接入 MA、MACD、RSI、ATR，统一参数传递和结果结构。
  - 完成条件：四种指标可由 Server API 返回，且包含 marketTime/engine 信息。
  - 验证方式：用固定 K 线 fixture 与独立计算结果做容差对比。

- [x] T029：实现 Chip Adapter
  - 涉及范围：接入 DSA 筹码结果并补 engineVersion、calculatedAt、provider。
  - 完成条件：Position Detail 能得到统一 ChipDistribution；异常时返回可解释错误。
  - 验证方式：固定股票和日期执行两次，输出在相同输入下保持一致。

- [x] T030：建立 Account 数据模型与迁移
  - 涉及范围：包含 name、source、type、broker、currency、createdAt、updatedAt。
  - 完成条件：数据库存在 account 表及索引；source 支持 manual/alipay/ths/broker。
  - 验证方式：Migration 后创建四类账户 fixture，查询结果正确。

- [x] T031：实现 Account CRUD API
  - 涉及范围：提供创建、查询、更新、删除/停用账户能力，并校验名称、币种和 source。
  - 完成条件：Desktop 可通过 API 管理账户；删除有持仓账户时遵循明确规则。
  - 验证方式：API 测试覆盖正常、重复、非法币种和有持仓删除场景。

- [x] T032：建立 V0.1 Position 输入模型
  - 涉及范围：建立 accountId、symbol、quantity、costPrice、source、updatedAt；明确这是 V0.3 前的过渡事实模型。
  - 完成条件：Position 数据可按账户查询、唯一约束合理，quantity/costPrice 有数值校验。
  - 验证方式：迁移后插入、更新、删除持仓并检查约束。

- [x] T033：实现手动持仓录入
  - 涉及范围：Desktop/Server 支持选择账户、标的、数量、成本价创建持仓。
  - 完成条件：录入后立即可参与 Portfolio 估值；非法数量/价格被阻止。
  - 验证方式：录入 600519.SH 100 股，查询 Portfolio 检查成本和数量。

- [x] T034：实现 Position 编辑与删除
  - 涉及范围：支持修正数量、成本、账户和删除错误持仓，记录更新时间。
  - 完成条件：UI 与 API 均可完成修改；删除后 Portfolio 立即重算。
  - 验证方式：修改数量、成本各一次，再删除并验证总资产变化。

- [x] T035：实现 Screenshot Upload
  - 涉及范围：支持 PNG/JPG/JPEG/WebP，限制大小、MIME、文件名和临时文件生命周期。
  - 完成条件：上传后返回 import session，不直接写 Position；非法文件被拒绝。
  - 验证方式：上传四种格式和一个伪装扩展名文件，验证行为。

- [x] T036：定义 PositionVisionProvider Contract
  - 涉及范围：抽象图片到结构化候选数据的 Provider，允许 DSA Vision/OpenAI/Gemini 等实现。
  - 完成条件：Screenshot Import 不直接依赖具体模型 SDK；Provider 可替换。
  - 验证方式：使用 Mock Provider 完成一次完整 import draft，证明流程不依赖真实模型。

- [x] T037：实现截图来源识别
  - 涉及范围：识别 alipay/ths/broker/unknown，并允许用户在 Review 页面修正来源。
  - 完成条件：每个 import draft 都有 source 与 confidence；unknown 不阻断后续手动确认。
  - 验证方式：使用支付宝、同花顺、券商和无关截图 fixture 验证分类。

- [x] T038：实现持仓字段提取
  - 涉及范围：从截图提取 name、symbol、quantity、costPrice、marketPrice、marketValue、profit、profitRate。
  - 完成条件：每个字段保留 confidence 和 rawText；缺失字段不编造。
  - 验证方式：对 Ground Truth 数据集逐字段计算准确率和缺失率。

- [x] T039：实现 Asset Matching
  - 涉及范围：使用 symbol 优先、name/简称/别名辅助，输出 matched/ambiguous/unmatched。
  - 完成条件：匹配过程可解释；ambiguous 必须要求用户确认。
  - 验证方式：测试代码准确、仅名称、同名歧义、已更名证券四类场景。

- [x] T040：实现截图数值一致性校验
  - 涉及范围：验证 quantity、costPrice、marketValue、profit、profitRate 的数学关系和合理范围。
  - 完成条件：不一致项进入 warning/error，不允许 Vision 结果无条件提交。
  - 验证方式：人为修改 marketValue/profit fixture，确认能检测异常。

- [x] T041：实现 Import Draft 持久化
  - 涉及范围：保存原图引用、识别结果、匹配结果、warning、状态和过期时间。
  - 完成条件：Draft 与正式 Position 分表/分状态；未确认 Draft 不影响 Portfolio。
  - 验证方式：创建 Draft 后查询 Portfolio，确认资产不变化。

- [x] T042：实现 Import Review UI
  - 涉及范围：桌面端展示每条候选持仓，支持修改、删除、补代码、换账户、查看 warning。
  - 完成条件：用户可在提交前纠正任何关键字段；低置信度有明显标记。
  - 验证方式：使用包含 matched/ambiguous/unmatched 的 fixture 完成一次人工 Review。

- [x] T043：实现 Import Commit
  - 涉及范围：将审核后的 Draft 原子写入 Position，并更新 import 状态和变更记录。
  - 完成条件：重复点击提交不会产生重复持仓；失败时不产生半写入状态。
  - 验证方式：模拟数据库失败验证事务回滚；连续提交两次验证幂等。

- [x] T044：实现重复导入检测
  - 涉及范围：使用 image hash、account、position fingerprint 识别同截图/同快照重复导入。
  - 完成条件：重复导入给出提示并要求显式覆盖或取消，不静默叠加数量。
  - 验证方式：同一截图连续上传两次、轻微裁剪一次，验证检测策略符合设计。

- [x] T045：实现 Import History 与 Rollback
  - 涉及范围：保存每次导入前后差异，并允许回滚最近一次截图导入。
  - 完成条件：回滚后 Position 恢复到导入前状态；历史记录不可丢失。
  - 验证方式：导入→修改→回滚，验证 Position 和 history。

- [x] T046：实现 Portfolio 估值计算
  - 涉及范围：输入 Account、Position、Quote，计算 marketValue、totalCost、unrealizedPnL、unrealizedPnLPct、weight。
  - 完成条件：单账户和全账户结果可重复计算；缺报价时有 dataQuality/limitations。
  - 验证方式：用手工可算的三持仓 fixture 对比计算结果。

- [x] T047：实现 Portfolio Summary API
  - 涉及范围：返回 totalMarketValue、totalCost、totalPnL、totalPnLPct、accountCount、positionCount 和账户分组。
  - 完成条件：Desktop/Mobile 只依赖 Investment OS API 获取 Portfolio。
  - 验证方式：API 测试覆盖多账户、空账户、缺行情。

- [x] T048：实现 Desktop Dashboard
  - 涉及范围：展示总资产、浮盈亏、账户分布、持仓列表、最大盈利/亏损和当前风险摘要。
  - 完成条件：页面能在 loading/empty/error/stale 状态下正确展示。
  - 验证方式：用空数据、正常数据、DSA 不可用三种环境人工验收。

- [x] T049：实现 Position Detail
  - 涉及范围：展示实时价、成本、收益、K线、MA/MACD/RSI/ATR 和筹码摘要。
  - 完成条件：所有行情/指标/筹码均来自统一 Contract；不显示来源不明的数值。
  - 验证方式：打开一个持仓详情并核对各组件时间戳与 Provider。

- [x] T050：建立 RiskRule V0.1 模型
  - 涉及范围：字段包含 type、scope、target、parameters、severity、enabled、createdAt、updatedAt。
  - 完成条件：支持固定价止损、成本止损、止盈、价格提醒、单股集中度五类规则。
  - 验证方式：数据库测试创建五类规则并成功反序列化。

- [x] T051：实现固定价格止损规则
  - 涉及范围：当 price < threshold 时生成 RiskEvent，并支持 enabled/severity。
  - 完成条件：同一行情输入下规则判断确定性；缺报价不误触发。
  - 验证方式：构造高于、等于、低于阈值三组价格测试。

- [x] T052：实现成本百分比止损与止盈
  - 涉及范围：根据 Position 成本和 Quote 计算 PnL%，判断 `PnL < -X%` 与 `PnL > X%`。
  - 完成条件：计算逻辑不由 AI 完成；边界值行为有明确约定。
  - 验证方式：测试 -8%、0、+20% 以及成本为 0 的异常情况。

- [x] T053：实现价格提醒规则
  - 涉及范围：支持 price > X 和 price < X 两个方向，并生成统一 RiskEvent。
  - 完成条件：规则可绑定 symbol；触发值和 threshold 被持久化。
  - 验证方式：自动化测试上下穿越阈值场景。

- [x] T054：实现单股集中度规则
  - 涉及范围：根据 Portfolio weight 判断单一持仓是否超过阈值。
  - 完成条件：权重以同一 Portfolio snapshot 为准，现金/缺报价处理有定义。
  - 验证方式：构造 10%、20%、30% 三持仓组合验证。

- [x] T055：实现 Risk Evaluation 流程
  - 涉及范围：行情更新或主动扫描时加载相关规则、Portfolio 上下文并输出事件。
  - 完成条件：评估失败不会阻断其他规则；每次扫描有 traceId。
  - 验证方式：同时配置 5 条规则，验证单条异常不影响其它评估。

- [x] T056：实现 RiskEvent 持久化
  - 涉及范围：保存 ruleId、accountId、symbol、severity、triggerValue、threshold、message、triggeredAt。
  - 完成条件：事件可查询历史；同一事件与通知解耦。
  - 验证方式：触发规则后查询数据库并核对上下文。

- [x] T057：定义 NotificationProvider 并接入飞书
  - 涉及范围：统一 send(notification) 契约，V0.1 实现 Feishu Webhook；可复用 DSA 底层实现但不复用业务编排。
  - 完成条件：RiskEvent 可独立映射为通知；发送成功/失败可观察。
  - 验证方式：使用测试群机器人发送一条固定消息和一条 RiskEvent。

- [x] T058：实现 Notification cooldown 与 dedup
  - 涉及范围：按规则/标的/事件 key 限频，避免行情持续越界导致刷屏。
  - 完成条件：TTL 内重复事件不重复发送；TTL 后可再次发送。
  - 验证方式：连续触发相同规则 3 次，确认只收到 1 次；模拟 TTL 后再次收到。

- [x] T059：持久化 Notification Delivery Result
  - 涉及范围：记录 provider、status、attempt、response summary、sentAt、errorCode。
  - 完成条件：可区分 RiskEvent 已触发但通知失败的情况。
  - 验证方式：模拟 Feishu 4xx/5xx 和成功响应，检查记录。

- [x] T060：建立 AI Gateway 与 Provider 抽象
  - 涉及范围：统一 model、baseURL、key、timeout、request metadata，支持至少一个可用模型和 Mock。
  - 完成条件：业务模块不直接调用具体 SDK；配置切换无需改业务代码。
  - 验证方式：用 Mock 与真实 Provider 分别完成相同 prompt 调用。

- [x] T061：建立 AI Tool Registry
  - 涉及范围：V0.1 注册 getPortfolio、getPositions、getQuote、getBars、getIndicators、getChipDistribution、getRisk。
  - 完成条件：Tool 有输入 Schema、权限、超时和结构化输出。
  - 验证方式：逐个执行七个 Tool 的契约测试。

- [x] T062：实现 AI Portfolio Analysis
  - 涉及范围：AI 基于 Tool 获取真实持仓、行情、盈亏和风险，不直接读数据库表。
  - 完成条件：回答能指出主要持仓和风险，并显示数据时间；关键数字来自 Tool。
  - 验证方式：使用固定 Portfolio fixture 检查回答中的数值与 Tool 输出一致。

- [x] T063：实现 AI Risk Explanation
  - 涉及范围：针对 RiskEvent 拉取 Position、Quote、Indicator、Chip 等上下文，生成解释而不是重新计算触发条件。
  - 完成条件：解释必须引用已触发规则、阈值和数据时间；Tool 失败时明确说明缺失。
  - 验证方式：构造固定 RiskEvent 验证解释中 threshold/triggerValue 精确匹配。

- [x] T064：记录 AI Provenance V0
  - 涉及范围：保存 model、promptVersion、toolCalls、provider、marketTime 和最终输出引用。
  - 完成条件：每次 AI 分析均可追溯输入来源；不记录明文 Secret。
  - 验证方式：查询一条分析记录并能还原所用 Tool 与行情时间。

- [x] T065：初始化 React Native Mobile
  - 涉及范围：建立移动端导航、API Client、环境配置和基础错误处理。
  - 完成条件：Mobile 可以访问同一 Investment OS API；不直接调用 DSA。
  - 验证方式：真机/模拟器打开 Dashboard 并成功拉取测试接口。
  - 收尾进度：已接入 Expo/React Native runtime、Android/iOS native prebuild、Metro/Babel、EAS profile、API 环境入口和错误状态；Android API fallback 使用 `10.0.2.2`，生产仍要求显式 `EXPO_PUBLIC_API_BASE_URL`，且 Expo SDK 57 依赖已通过 `expo install --check`。2026-08-01 已在 Android API 35 模拟器冷启动 Dashboard 并成功读取隔离 fixture；最新 APK/AAB 与设备证据归档见 `docs/reviews/mobile-runtime-review.md` 和 `docs/reviews/evidence/mobile-android/`。iOS generic archive 仍受 `DVTDownloads` 系统框架版本不匹配阻塞。

- [x] T066：实现 Mobile 只读 Portfolio 与 Risk
  - 涉及范围：移动端显示总资产、持仓和 RiskEvent 列表；V0.1 不实现复杂截图 Review。
  - 完成条件：与 Desktop 同一账户数据一致；stale/error 状态可见。
  - 验证方式：同一测试账户在 Desktop/Mobile 对比数量、成本、风险。
  - 收尾进度：已实现 RN Portfolio/Risk 页面、只读 Store、Decimal 归一化、陈旧标识及 loading/empty/error/stale 契约测试，并增加并发刷新保护；Web bundle 与移动端 6 项测试通过。Android API 35 模拟器和 macOS Desktop release 已使用同一隔离 `fixture-account` 对照 Portfolio 数值、Risk 事件及 ready/stale/error 状态，证据见 `docs/reviews/evidence/mobile-android/desktop-mobile-fixture-comparison.md`；真实 Compose/生产账户仍由发布门禁负责。

- [x] T067：建立 Screenshot Ground Truth 数据集
  - 涉及范围：至少收集脱敏的支付宝×5、同花顺×5、券商×5，并人工标注 source/symbol/quantity/cost/marketValue/profit。
  - 完成条件：数据集可版本化且不含个人敏感信息。
  - 验证方式：运行校验脚本确认每个样本都有 Ground Truth 和匿名化检查。

- [x] T068：建立 Screenshot Regression 测试
  - 涉及范围：每次修改 Vision Prompt/Provider 后自动对数据集计算来源识别率、字段准确率、匹配率。
  - 完成条件：基准结果入报告；准确率下降超过阈值会失败。
  - 验证方式：故意降低一个 fixture 识别结果，确认测试能发现回归。

- [x] T069：建立 V0.1 核心 E2E
  - 涉及范围：覆盖创建账户→截图→Review→Commit→Portfolio→触发止损→飞书→AI Explain。
  - 完成条件：整个链路可在测试环境一键执行，关键外部依赖可 Mock。
  - 验证方式：CI 或本地运行 E2E 全绿，并保存一次人工真实环境验证记录。
