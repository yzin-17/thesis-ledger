# V1.0：稳定性、发布与最终验收

> 阶段目标：把各阶段能力产品化：迁移、备份、安全、可观测性、性能、跨端发布、测试和最终一致性 Review。

- [ ] T255：执行 Domain Model 总审计
  - 涉及范围：Review Account/Ledger/Position/Portfolio/Risk/Strategy/Journal/Automation 的关系和冗余字段。
  - 完成条件：不存在互相冲突的事实源；废弃字段有迁移计划。
  - 验证方式：生成 domain map 并逐表检查 owner/source-of-truth。

- [ ] T256：建立 Migration 测试矩阵
  - 涉及范围：覆盖从空库、V0.1、V0.3、当前版本升级到 V1.0。
  - 完成条件：所有支持路径可自动执行并保持数据完整。
  - 验证方式：在多个数据库快照上跑 migration CI。

- [ ] T257：建立回滚与恢复策略
  - 涉及范围：明确数据库 migration、应用版本、DSA image 的回退流程。
  - 完成条件：出现发布问题能恢复到上一兼容版本。
  - 验证方式：在 staging 演练一次升级→回退。

- [ ] T258：实现数据完整性检查命令
  - 涉及范围：检查 Ledger balance、Position projection、Snapshot、orphan FK、重复 externalUid 等。
  - 完成条件：可输出错误报告并给出修复建议，不自动破坏数据。
  - 验证方式：故意制造异常 fixture 验证检测。

- [ ] T259：实现数据库 Backup
  - 涉及范围：提供本地/部署环境备份脚本和保留策略。
  - 完成条件：备份文件带时间、版本和校验。
  - 验证方式：执行一次全库备份。

- [ ] T260：实现 Restore
  - 涉及范围：支持从备份恢复到空环境，并验证 migration 兼容。
  - 完成条件：恢复后核心 E2E 数据完整。
  - 验证方式：备份→删除库→恢复→执行 integrity check。

- [ ] T261：实现用户数据导出
  - 涉及范围：导出 Account、Ledger、Portfolio、Journal、Strategy、Risk/Notification history 的结构化文件。
  - 完成条件：导出格式有版本；不包含 Secret。
  - 验证方式：导出测试账户并检查内容。

- [ ] T262：执行 Secret/Credential 最终安全审计
  - 涉及范围：检查 AI Key、Provider Key、Feishu Webhook、数据库凭据的存储和日志。
  - 完成条件：Secret 均加密或环境化并脱敏。
  - 验证方式：运行 secret scanner + 手动日志 Review。

- [ ] T263：实现 Upload Security 加固
  - 涉及范围：限制文件大小/类型、路径、临时文件权限和清理；防止恶意文件名或超大文件。
  - 完成条件：截图导入不执行文件内容；临时文件按策略清理。
  - 验证方式：安全测试伪 MIME、超大文件、路径穿越名称。

- [ ] T264：实现 API 输入验证与限流
  - 涉及范围：所有公开 API 使用 Schema，上传/AI/重任务有合理限流。
  - 完成条件：非法输入统一错误，不泄漏堆栈。
  - 验证方式：Fuzz/边界输入测试。

- [ ] T265：实现日志脱敏与结构化日志
  - 涉及范围：统一 traceId、service、operation、duration、status，脱敏 token/webhook/PII。
  - 完成条件：跨 Server→DSA 调用可用 traceId 关联。
  - 验证方式：执行一次请求并检索完整链路。

- [ ] T266：接入 Error Tracking
  - 涉及范围：捕获 Server、Desktop 关键异常和版本信息，不上传敏感 Portfolio 内容。
  - 完成条件：staging 能看到受控错误事件。
  - 验证方式：主动抛错验证。

- [ ] T267：建立 Metrics
  - 涉及范围：至少覆盖 API latency/error、Provider health、Job、Import、Notification、AI、Backtest。
  - 完成条件：能回答系统哪里慢、哪里失败。
  - 验证方式：生成负载并检查指标变化。

- [ ] T268：实现 Provider/Automation 运维 Dashboard
  - 涉及范围：展示数据源健康、最后同步、队列、失败 job、通知失败。
  - 完成条件：核心故障不需要查数据库即可看到。
  - 验证方式：注入 Provider/Job 故障人工验收。

- [ ] T269：完成 Portfolio 性能基准
  - 涉及范围：测量 10/50/200/1000 持仓估值、风险扫描和 Dashboard API。
  - 完成条件：记录目标阈值并满足个人端可用体验。
  - 验证方式：运行 benchmark 保存报告。

- [ ] T270：优化批量 Quote 与增量计算
  - 涉及范围：避免每持仓单独请求；行情变更只重算必要的 Portfolio/Risk。
  - 完成条件：调用次数和延迟相较基线明显下降且结果一致。
  - 验证方式：对比优化前后 benchmark 与 checksum。

- [ ] T271：完成数据库索引 Review
  - 涉及范围：基于实际 query plan 优化 Ledger、Bar、RiskEvent、Job、Snapshot 查询。
  - 完成条件：关键查询无明显全表扫描。
  - 验证方式：保存 EXPLAIN ANALYZE 报告。

- [ ] T272：实现 Desktop Production Build
  - 涉及范围：Electron 正式构建、环境切换、签名配置入口和静态资源打包。
  - 完成条件：macOS/Windows 均能生成可安装产物。
  - 验证方式：在两个平台安装启动并完成基础 E2E。

- [ ] T273：实现 Desktop Auto-update 策略
  - 涉及范围：若启用，定义更新源、版本兼容和失败回滚；若 V1 不启用则形成明确文档决策。
  - 完成条件：不存在未设计的隐式自动升级。
  - 验证方式：测试更新或验证关闭状态。

- [ ] T274：实现 React Native Android Release Build
  - 涉及范围：配置 production API、签名、版本号、权限和基础网络策略。
  - 完成条件：生成可安装 APK/AAB 并运行 Portfolio/Risk。
  - 验证方式：真实或模拟 Android 验收。

- [ ] T275：实现 React Native iOS Release Build
  - 涉及范围：配置 production API、版本、权限和安全网络。
  - 完成条件：生成可运行 TestFlight 或本地 release build。
  - 验证方式：iOS 设备或模拟器验收。

- [ ] T276：统一 Loading/Empty/Error/Stale UX
  - 涉及范围：Desktop/Mobile 对 Portfolio、Market、Risk、Import、AI 建立一致状态组件。
  - 完成条件：数据陈旧与错误不会展示成正常最新值。
  - 验证方式：注入五类状态逐页验收。

- [ ] T277：完成 First-run Onboarding
  - 涉及范围：引导创建账户、导入或手动持仓、配置飞书和数据源，并说明风险提醒限制。
  - 完成条件：新用户无需阅读开发文档即可跑通基础闭环。
  - 验证方式：全新用户环境执行 onboarding。

- [ ] T278：建立 Accessibility/Responsive Review
  - 涉及范围：检查键盘、焦点、基础对比度、不同窗口尺寸和移动端小屏。
  - 完成条件：关键流程无明显不可操作区域。
  - 验证方式：按 checklist 在 Desktop/Mobile 测试。

- [ ] T279：建立完整 Domain Unit Test 套件
  - 涉及范围：覆盖 Ledger、Performance、Risk、Strategy schema、Behavior metrics 等核心纯逻辑。
  - 完成条件：核心计算模块达到约定覆盖率并有边界案例。
  - 验证方式：CI 生成 coverage 报告。

- [ ] T280：建立 Adapter Contract Test 套件
  - 涉及范围：覆盖 DSA、各 Market Provider、AI Provider、Notification Provider。
  - 完成条件：外部升级导致结构变化能被测试捕获。
  - 验证方式：升级或 Mock 一次不兼容响应确认失败。

- [ ] T281：建立数据库集成测试
  - 涉及范围：使用真实 PostgreSQL/Redis 容器测试 migration、事务、锁、队列、幂等。
  - 完成条件：不只依赖内存数据库。
  - 验证方式：CI Testcontainers/Compose 通过。

- [ ] T282：建立 Screenshot/Chip/Backtest/Risk 固定基准集
  - 涉及范围：将关键算法输入输出 versioned fixture 化。
  - 完成条件：后续版本结果漂移有明确 diff。
  - 验证方式：运行 regression report 并归档。

- [ ] T283：建立 Desktop E2E
  - 涉及范围：覆盖账户、截图、Ledger、Portfolio、Risk、AI、Strategy、Journal、Automation 配置。
  - 完成条件：主要用户路径在 release build 可跑。
  - 验证方式：执行 E2E 并保存报告。

- [ ] T284：建立 Mobile E2E
  - 涉及范围：覆盖进入、Portfolio、Position、Risk、AI 基础查看和错误状态。
  - 完成条件：Android/iOS 至少一套自动化或稳定人工 checklist。
  - 验证方式：执行并归档结果。

- [ ] T285：完成 README 与安装文档
  - 涉及范围：包括系统定位、架构、快速开始、Docker、Desktop/Mobile、DSA Fork。
  - 完成条件：新环境按文档能完成启动。
  - 验证方式：由未参与开发者按 README 从零安装。

- [ ] T286：完成 Provider、Import、Risk、Strategy、AI、Automation 使用文档
  - 涉及范围：每个核心模块包含概念、配置、常见错误和数据限制。
  - 完成条件：与 V1 UI/API 一致，不保留旧版本路径。
  - 验证方式：逐篇文档 Review 和链接检查。

- [ ] T287：建立 THIRD_PARTY_LICENSES / NOTICE
  - 涉及范围：记录 DSA、InStock、QuantStats 及移植代码的许可证和 attribution。
  - 完成条件：所有第三方代码/依赖满足对应许可证要求。
  - 验证方式：许可证扫描 + 人工核对移植文件。

- [ ] T288：完成 DSA Fork Delta Audit
  - 涉及范围：分类上游原样、本地 patch、本地 extension，并记录长期维护成本。
  - 完成条件：每个 fork 改动都有原因和测试覆盖。
  - 验证方式：对 `git diff upstream/main...` 做逐项 Review。

- [ ] T289：建立 DSA Upstream Merge Playbook
  - 涉及范围：定义同步频率、流程、Contract/Regression 测试和冲突处理。
  - 完成条件：未来维护者可按文档升级 upstream。
  - 验证方式：在临时分支演练一次同步。

- [ ] T290：执行 V1 核心 E2E
  - 涉及范围：覆盖创建账户→截图→Ledger→Portfolio→实时行情→Risk→Feishu→AI→Trade Plan→Journal→Backtest→日报→复盘。
  - 完成条件：整条链路在 release candidate 环境通过，无手工数据库修正。
  - 验证方式：保存一次完整 E2E 日志/checklist。

- [ ] T291：执行灾难恢复演练
  - 涉及范围：模拟数据库丢失、DSA 不可用、Provider 主源故障和通知故障。
  - 完成条件：备份可恢复；DSA/Provider 故障按设计降级；通知失败可重试/追踪。
  - 验证方式：按 runbook 实际演练并记录结果。

- [ ] T292：执行最终 Spec Traceability Review
  - 涉及范围：把 Spec 每个验收标准映射到任务、测试、实现或明确延期项。
  - 完成条件：不存在“Spec 有要求但任务包无覆盖”的条目。
  - 验证方式：产出 `spec-traceability.md` 并逐条勾选。

- [ ] T293：执行最终架构一致性 Review
  - 涉及范围：检查客户端只调 Investment OS、Ledger 是事实源、DSA 是可替换能力服务、第三方均经 Adapter。
  - 完成条件：无跨边界违规；例外全部有 ADR。
  - 验证方式：静态搜索、依赖图和人工 Review。

- [ ] T294：完成 V1 Release Checklist 与版本发布
  - 涉及范围：确认 migration、backup、security、licenses、E2E、docs、build artifacts、known limitations。
  - 完成条件：打 V1.0 tag/release，发布说明包含升级和限制。
  - 验证方式：从 release artifact 在干净环境完成最后 smoke test。
