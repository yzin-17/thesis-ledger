# 开发数据库重建规格

> 任务标识：DEV-DB-REBUILD
> 日期：2026-09-14
> 状态：实现、隔离验证与当前开发环境部署验收完成，归档
> 对应任务：[实施任务](../tasks/2026-09-14-dev-database-rebuild.md)

## 背景与目标

交接记录报告：持久化开发库停留在 baseline，Compose 只挂载部分初始化 SQL，应用在访问缺失的策略风险表时退出。PostgreSQL 进程健康不能证明业务结构完整。开发阶段允许丢弃历史数据，需要通过显式重建恢复源码、结构输入和启动顺序的一致性。

## 范围与边界

主仓拥有数据库结构输入、重建执行器、结构版本与完整性校验。infra 拥有 Compose、目标数据库选择、应用停启和运维入口。Prisma model 表与 `raw-owned-tables.json` 登记的表都属于重建结果。

开发路径将现有全部 migration SQL 作为排序后的结构构建输入，不调用 Prisma Migrate，不维护 `_prisma_migrations`，也不以 `prisma db push` 替代完整结构构建。历史 migration 文件保持不变。正式发布保留独立的迁移路径；本主题不实现正式数据升级，不将开发重建用于发布部署。

不修改市场图表业务、不清理既有工作区、不删除持久卷，不处理 Dockerfile 文本变换机制的整体重构。

## 设计与可观察行为

1. 默认更新不丢弃数据。重建使用 `DEV_DATABASE_MODE=rebuild`、`DEV_DATABASE_ALLOW_DATA_LOSS=true` 和 `DEV_DATABASE_CONFIRM` 精确目标确认；执行器仅接受开发环境。目标确认包含 Compose 项目及数据库名，直接执行器需核对实际数据库与目标。配置错误在破坏性 SQL 之前失败；日志不输出密码或连接串。
2. 主仓按目录排序发现全部结构 SQL，输入缺失或非法时失败。使用同一组输入确定当前结构 head，避免只挂载一部分 SQL 或手工维护版本号。
3. infra 在执行前停止连接该库的 ThesisLedger server 和已配置的 worker；成功构建镜像和校验重建条件后才进入停机与重建阶段。
4. 执行器重建目标数据库的 `public` schema，执行全部结构输入和 app role 权限初始化，核对表覆盖并写入、核对当前 head。任一 SQL 或校验失败时返回非零；尽量将结构与版本发布放入一个事务，避免部分成功被识别为可启动。
5. 只有成功完成结构检查才允许 server/worker 启动。默认非重建更新也必须识别不匹配结构并阻止新版应用启动，给出明确修复入口。
6. 重建可重复执行；每次显式执行都会清空目标业务数据。PostgreSQL 存活检查与业务结构就绪检查各自表达真实语义。

## 数据与兼容性

开发数据不会被转换或保留。执行边界只包含经确认的目标库 `public` schema 和所需角色授权，不删除整个 PostgreSQL volume。相同 head 的判定必须配合所需表检查；版本值本身不能掩盖 raw-owned 表缺失。

## 测试策略

先做执行器的配置拒绝、输入发现、排序、失败停止和表清单覆盖测试，再验证 infra 停启编排和结构门禁。使用本任务新建的隔离 PostgreSQL 容器验证空库、baseline 库、重复重建、权限恢复及 SQL 失败回滚；使用同一环境复用镜像。

当前开发库实际重建与 server/worker 健康验证是独立部署验收。隔离数据库成功不代表当前服务已修复。只有精确目标与数据丢失开关确认后，才执行现有库重建。

## 风险与备选方案

全部 SQL 必须能够从空结构顺序构建，事务兼容性须在盘点与隔离验证中确认。若未来 migration 引入事务外操作，必须明确拒绝或修订执行契约。单独 `db push` 缺少 raw-owned 结构；继续手工挂载增量 SQL 会延续遗漏风险。

## 未决问题

### Blocking

- 实施设计问题：无。T0 已确认 7 个结构输入、65 张表（58 个 Prisma model 与 7 个 raw-owned 表）、server 与 `backtest-worker` 两个消费者。已有 SQL 的合法首尾事务边界须在装配时规范化；权限脚本包含 psql 元命令，应由支持该协议的执行端消费。
- 部署问题：无。用户已确认精确目标和数据丢失开关，G2 已完成。

### Non-blocking

- 正式发布的保留数据升级策略留在独立发布流程；本次仅维护其与开发路径的隔离。

## 验收标准

- AC1：默认不重建；缺少显式授权开关、开发约束或精确目标不匹配时，拒绝破坏性操作。
- AC2：自动发现全部结构 SQL，排序执行后覆盖 Prisma 与 raw-owned 表，不执行 Prisma Migrate 或创建其迁移历史。
- AC3：权限、表覆盖和当前 head 同步成功才返回成功；输入或 SQL 失败不会发布成功结构状态，重复重建得到完整空业务库。
- AC4：infra 先停止数据库消费者，再执行重建，成功后启动；失败不启动应用；非重建更新对结构不匹配明确失败。
- AC5：版本和部署结构输入自动跟随主仓；新增 SQL 不需要手工追加 Compose 挂载或 head 常量，门禁能发现覆盖遗漏。
- AC6：隔离 PostgreSQL 证明空库、旧 baseline、重复执行、授权和故障路径；现有开发库部署另行证明策略风险表可访问与 server/worker 健康。
- AC7：正式发布路径保持独立，历史 migration 不改写，既有工作区与持久卷保留，文档准确区分已实现与真实运行验证。
