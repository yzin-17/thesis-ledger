## 必须调整的地方

### 1. 表达式拆分已有修正，按实际依赖维护验证基线

当前拆分将表达式移到 `backtest-expression.ts`，交易计划在模块初始化时使用 `booleanExpressionSchema.optional()`。首次定向测试遇到 `positiveIntegerSchema` 缺失；检查期间该变量补回。第一次源码变更后复核，交易计划套件在导入时出现 `Cannot read properties of undefined (reading 'optional')`。

当时核对到运行时依赖环：

```text
backtest-trade-plan.ts
  → backtest-expression.ts
  → backtest-indicators.ts
  → backtest-contract.ts
  → backtest-strategy.ts
  → backtest-trade-plan.ts
```

其中 `backtest-indicators.ts` 曾从聚合合同取得底层周期、行情字段，表达式又从指标合同取得指标名称。定稿前该导入已改为底层 `backtest-values.ts`，表达式的公司行动枚举也改从值合同读取；随后只重验受变更影响的三个套件，全部 26 项通过。这项中间态故障不再作为当前阻塞，但后续扩展仍应维持低层值、表达式、策略组合的单向依赖，并按实际输入变化重验。相关测试并不证明目标服务已经更新。

### 2. “完整编辑”必须包含后来新增的正式配置

原方案仅列举基本条件、指标、仓位和固定风控，已经不足以覆盖现在的配置。现行 `tradePlan` 至少包括初始保护、追踪和激活、风险预算、冷却、净亏损暂停、具名加减仓、每日波动率仓位、月末目标仓位；当前源码还在接入会话数值与保护条件。

新的覆盖矩阵应逐组列明：正式配置、模型完整/精简输出、可视编辑、JSON、中文回读、保存、冻结与执行。区分“已有表达式”“交易计划专用表达”“正在实施”和“尚不支持”，不能把未交付能力显示成可执行，也不能让已保存但暂不可视编辑的内容在往返时丢失。加仓涨幅、加仓数量比例、权益上限等字段复用各自单位及比例说明，不能只显示泛化的“百分比”。

交易计划子任务的分项证据继续由该子任务维护；父任务仅同步边界和引用，不重复运行已经验收且输入未变的真实模型样本。当前会话及保护条件源码的存在，不能代替它们的正式任务和目标运行态验收。

### 3. 复用完整回读，修复仍然分叉的消费者

`packages/domain/src/backtest-strategy-plan-readback.ts` 已能区分 MACD 快慢/信号周期及输出线，现有定向测试通过。两端自然语言确认、部分详情和摘要已经消费它。

但是 `packages/schemas/src/backtest-price-research-strategy.ts` 的简略摘要仍主要读取 `params.period`，没有完整表达 MACD 多参数及输出线；Mobile 手动编辑器、研究转换预览等仍消费这条路径。因此最初发现的摘要碰撞不能按“所有页面都未修复”处理，也不能按“公共函数已修复、所有入口都通过”结案。应统一显示投影与消费者，并补两个 MACD 配置在手动编辑、AI 确认、详情和转换预览中的可辨认性对照。

### 4. 保存一致性仍是独立且必要的交付

Desktop 的 `StrategyEditorSheet.submit` 和 Mobile 的 `validatedDefinition` 仍在正式提交前调用价格投影。该函数会根据比较条件决定来源口径、生成来源副本、改写引用并筛掉未使用来源。后来增加的 ATR 来源保留处理只覆盖相应交易计划依赖，没有改变这项基本行为。

普通保存应严格校验并尊重用户显式定义；旧策略协议升级也应保持来源身份、引用、原值和已有语义。“转换成新的价格研究策略”继续由已有显式预览流程负责，不能作为普通保存或无损协议升级的隐含步骤。往返测试要同时覆盖 `entry`、`exit`、计划中的来源和条件、未使用来源、高精度值及未应用 JSON 错误。

### 5. 风险消费者需要按端核对，不能继续整体列为“仅支持版本 2”

`apps/server/src/strategy-optimization/strategy-risk-plan.ts` 已允许正式 Schema 2/3，并检查记录版本与定义版本一致，保留规则映射完整性门禁。

Desktop 的 `StrategyRiskApplicationPanel.tsx` 和 `StrategyRiskApplicationsSection.tsx` 仍存在只筛选 Schema 2 的分支。剩余交付应围绕“后端接受且可转换的版本能被正确选择、预览和升级”验证，同时明确不可转换规则的原因；不能放宽真实账户边界来迁就协议统一。

### 6. 版本轴与任务拆分需要重新对账

当前正式策略 Schema 仍是 2/3；规则能力清单记录的三用途配置 v5，以及完整/精简生成合同的版本，是不同版本轴。不能把“模型用途配置已到 v5”解释成策略已升级到 Schema 5，也不需要因编辑器改造再次创建模型配置版本。

父任务已保留交易计划子任务的当前状态，但多项总括条目仍混合语言扩展、AI 生成、回读、协议迁移和客户端交付。后续应按当前可交付结果拆分依赖及验收，使用已有的验证结果；不能要求所有开放语言能力先完成，才开始支持已经就绪的编辑节点。尚未完成的既定范围继续留在活动任务，不转移到 TODO 来宣称完成。

## 建议的剩余执行顺序

1. **确认源码基线**：复用已通过的表达式及计划定向测试；继续变动的模块按实际依赖补验，固定可交付输入。
2. **当前定义和回读对账**：以现有正式 Schema 为准形成节点覆盖矩阵，统一完整回读和相应入口。交易计划及已交付能力直接复用。
3. **一个手动编辑纵向闭环**：先验证简单交叉条件及一条交易计划能在可视、JSON、回读、受控保存和冻结执行间保持一致，同时修复未应用文本及保存前隐式转换。
4. **共享草稿与双端逐组覆盖**：来源、递归条件、仓位/风控、交易计划、费用/基准分别交付；各自拥有本地检查、往返测试和边界。继续使用已选页签方式和显式来源同步。
5. **协议及所有生产者统一**：补齐 `native-nav`、`run`、历史显式升级和 NAV 准备/Worker/读取链；适配风险消费者和生成入口后再启用新定义写入门禁。不得改变独立运行协议版本或历史摘要。
6. **分别执行目标环境门禁**：历史重放、队列/Worker、两端实际页面及必要原生场景分别保留证据。既有真实模型证据按实际覆盖复用，不把组件或 Web 宿主结果扩大成原生设备验收。

该顺序是对原方案依赖的修订，不是新的功能范围或验收豁免；具体当前执行状态继续由父任务及各子任务维护。
