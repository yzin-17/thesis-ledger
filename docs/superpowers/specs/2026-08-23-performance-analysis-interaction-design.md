# 收益分析交互优化设计

- 日期：2026-08-23
- 状态：方案已确认，待文档审阅
- 适用范围：`apps/desktop` 收益分析页面

## 背景

当前收益分析页把收益范围、账户、收益指标、历史 Snapshot、资产配置、再平衡建议和目标配置编辑依次铺在一个长页面中。数据虽然齐全，但用户需要自行推断各区块之间的关系。

现有界面还有四类容易造成误解的问题：

1. 页面级“暂无数据”可能与下方已有的资产配置和再平衡数据同时出现。
2. Snapshot 不足时，TTWROR 仍可能显示为 `0.00%`，容易被理解为已计算出的真实收益。
3. “实际收益 / 影子收益”和账户选择彼此独立，且页面默认选择第一个账户，没有明确的“全部账户”入口。
4. 持仓使用 `etf` 等领域分类键，目标配置允许填写 `ETF`、`股票` 等任意字符串，导致同一分类被当成不同对象，出现“资产配置为 100%，再平衡当前权重为 0%”的矛盾结果。

本设计采用“单页分析工作台 + 目标配置侧栏”。主页面负责解释收益、历史和配置偏差；编辑动作收进侧栏，避免内部 JSON 结构干扰日常阅读。

## 目标

1. 形成“选择分析范围 → 查看收益 → 理解数据状态 → 比较当前与目标 → 调整目标”的连续流程。
2. 让加载、空数据、陈旧数据和局部错误只影响对应区块，不再用一个页面级状态概括所有查询。
3. 合并资产配置与再平衡信息，让当前权重、目标权重、差额金额和建议可以逐行比较。
4. 用结构化表单替代默认 JSON 编辑，并在提交前完成权重合计校验。
5. 统一资产分类的领域键和展示名称，确保配置与再平衡建议基于同一分类语义。
6. 保持“只给建议、不自动下单”的产品边界。

## 非目标

- 不修改 TTWROR、XIRR、成本、现金或再平衡金额的计算公式。
- 不在本次设计中增加基准指数、超额收益、归因分析或交易执行能力。
- 不修改 Ledger、Position、Portfolio Snapshot 的领域边界。
- 不为此次页面调整重构其他功能模块。
- 第一阶段不增加时间区间筛选；收益走势图作为第二阶段增强。
- 当前 allocation 输入不包含现金，因此第一阶段不把现金作为可配置目标分类；若未来纳入现金，需要先扩展服务端 allocation 契约和计算测试。

## 信息架构

页面从上到下分为五个区域：

1. **页面标题与主操作**：左侧显示标题和说明，右侧提供“调整目标”。
2. **分析范围工具栏**：组合模式、账户范围和数据时点集中在同一行。
3. **收益概览**：最新总资产、时间加权收益和资金加权收益。
4. **收益历史**：第一阶段保留结构化明细和分区空状态；第二阶段增加走势图，并把明细收进可展开区域。
5. **配置与再平衡**：合并当前配置、目标配置和再平衡建议。

目标配置不再常驻页面底部。“调整目标”打开右侧 Sheet，保存后回到原分析上下文。

## 详细交互

### 1. 分析范围工具栏

- 将“实际收益 / 影子收益”改为“实际组合 / 影子组合”，强调这是数据范围而不是收益类型。
- 使用语义化 Tabs 表达两种互斥视图。
- 账户选择增加“全部账户”，默认值为“全部账户”，对应空 `accountId`。
- 账户列表只显示当前组合模式下的账户。
- 切换组合模式时，如果当前账户不属于新模式，自动回到“全部账户”；不得继续携带无效账户。
- 工具栏右侧显示最近一个完整 Snapshot 的时间。没有 Snapshot 时显示“尚无收益历史”，不伪造数据时点。
- 前端 Snapshot 类型需要保留服务端已有的数据质量标记，以区分完整、partial 和缺失行情的 Snapshot；不得只依据记录是否存在推断完整性。

### 2. 收益概览

保留三个指标，但调整空值语义：

| 指标 | 有效状态 | 无法计算状态 |
| --- | --- | --- |
| 最新总资产 | 显示最近完整 Snapshot 的市值与现金合计 | 显示“尚无 Snapshot” |
| 时间加权收益 | 至少两个完整 Snapshot 时显示 TTWROR | 显示 `—`，说明“至少需要两个完整快照” |
| 资金加权收益 | XIRR 可解时显示年化收益 | 显示 `—`，展示服务端返回的 `xirrReason` |

不得把“计算条件不足”显示为 `0.00%`。指标说明使用面向用户的中文，TTWROR、XIRR 作为辅助术语保留。

部分 Snapshot 缺失行情时，仅收益概览与历史区显示数据质量警告；资产配置仍可展示已有的可用市值，并明确缺失行情不会按零值处理。

### 3. 收益历史

第一阶段：

- 保留 Snapshot 明细，但使用独立的加载、空数据、错误和陈旧状态。
- 空状态说明生成条件，不渲染只有表头的空表。
- 明细继续展示时间、市值、成本和现金。

第二阶段：

- 使用现有 Snapshot 数据增加净资产走势。
- 图表默认展示总资产，不引入新的服务端计算口径。
- Snapshot 明细收进“查看明细”的可展开区域，图表加载失败不影响明细查看。
- 图表实现优先使用 shadcn Chart；引入 Recharts 前在实施计划中单独确认依赖变更。

### 4. 配置与再平衡

将“资产配置”和“再平衡缺口”合并成一张比较表：

| 分类 | 当前权重 | 目标权重 | 权重偏差 | 缺口金额 | 建议 |
| --- | ---: | ---: | ---: | ---: | --- |
| ETF | 100% | 40% | -60% | 对应金额 | 减配 |
| 股票 | 0% | 60% | +60% | 对应金额 | 增配 |

交互规则：

- 当前权重和目标权重使用同一尺度的轻量进度条辅助比较，数值仍是主要信息。
- “增配 / 减配 / 平衡”使用 Badge 表达，不使用只有颜色差异的文本。
- 未设置目标时只展示当前配置，并在区块标题处提供“设置目标”。
- 已设置目标时提供“调整目标”，与页面标题区的主操作打开同一个 Sheet。
- 缺失行情的分类保留明确提示，不按 `0` 参与当前权重计算。

### 5. 目标配置 Sheet

目标配置使用结构化行编辑器：

- 每行包含资产分类选择、百分比输入和删除操作。
- 支持新增分类，但同一分类不得重复。
- 权重以百分比显示，提交时转换为 `0–1` 的领域值。
- 底部实时显示合计值，例如“当前合计 85%，还差 15%”。
- 合计不等于 100%、存在负数、非有限数字或重复分类时，显示行内错误并禁用保存。
- 保存成功后关闭 Sheet、显示成功 Toast，并刷新目标与配置比较结果。
- 保存失败时保留用户输入，显示服务端错误，不关闭 Sheet。
- JSON 不再作为默认输入方式。本次实现不提供高级 JSON 编辑入口，避免为低频场景增加双向同步复杂度。

Sheet 必须提供可访问标题和说明。关闭存在未保存修改的 Sheet 时，需要二次确认；没有修改时直接关闭。

目标保存范围遵循现有领域规则：选择单个账户时保存 account 级目标，选择“全部账户”时保存 portfolio 级目标。`mode` 只改变分析数据范围，不创建实际/影子两套目标版本；portfolio 级目标继续由两种模式共享。

## 分类规范化

再平衡计算统一使用当前 allocation 契约支持的 `AssetType` 领域键：

| 领域键 | 展示名称 | 可识别旧值示例 |
| --- | --- | --- |
| `stock` | 股票 | `股票`、`STOCK` |
| `etf` | ETF | `ETF` |
| `fund` | 基金 | `基金`、`FUND` |
| `index` | 指数 | `指数`、`INDEX` |

规则如下：

1. Position 和 Performance Layers 的分类在进入配置计算前转换为领域键。
2. 新保存的目标配置只写入领域键，展示层负责转换中文名称。
3. 读取旧目标时识别上表中的别名；多个旧值映射到同一领域键时合并权重，权重总和保持不变。
4. 无法识别或当前契约暂不支持的旧分类（包括现金）不得静默丢弃。Sheet 显示“需要重新选择分类”，用户完成映射前禁止保存。
5. Allocation 和 Rebalance 请求必须使用同一份规范化后的分类集合。

该规范化是交互优化的前置正确性要求，不作为纯视觉调整处理。

## 组件边界

建议把页面拆成以下职责单一的组件：

- `PerformanceScopeToolbar`：管理模式、账户范围和数据时点展示。
- `PerformanceMetricGrid`：只负责三个收益指标及其解释状态。
- `PerformanceHistorySection`：负责 Snapshot 状态、明细和第二阶段走势图。
- `PerformanceAllocationSection`：负责当前、目标与再平衡的合并比较。
- `PerformanceTargetSheet`：负责目标草稿、校验、未保存确认和提交。
- 分类规范化 helper：负责领域键、展示名称和旧别名映射，不放入 JSX 条件分支。

页面容器负责组合这些组件和维护当前分析范围，不承担表单字段级状态。

## 数据流与请求状态

1. 用户选择 `mode` 和 `accountId`。
2. TanStack Query 按 `mode + accountId` 分别读取 history、summary 和 layers；targets 按 portfolio/account scope 读取。
3. layers 和 targets 先经过分类规范化，再请求 allocation/rebalance。
4. 新分析范围首次加载时显示对应区块 Skeleton，不展示上一个范围的数据。
5. 同一范围后台刷新时保留已有数据，并使用低干扰的“正在更新”状态。
6. 保存目标使用 Mutation；成功后失效 targets 和依赖它的 allocation/rebalance 查询，不使用手写的全页面 refetch 流程。

各区块独立派生状态：history 为空不能让 allocation 进入空状态；summary 错误不能隐藏仍可用的 Snapshot 明细。

## 错误与数据质量

- 页面级 Alert 只用于确实影响整个分析范围的错误，不再用于表达单个区块为空。
- summary 因 partial Snapshot 失败时，在收益概览与历史区显示缺失行情说明；配置区继续展示可用结果。
- allocation 失败时只影响配置与再平衡区，并提供该区块的重试操作。
- targets 读取失败时，当前配置仍可展示，但目标列和再平衡建议标记为不可用。
- XIRR 无解使用服务端 `xirrReason`；前端类型需要保留该字段。
- 所有错误状态不得用 `0`、空字符串或上一分析范围的数据代替。

## 分阶段实施

### 第一阶段：交互与正确性

1. 统一分析范围工具栏和“全部账户”行为。
2. 拆分区块级数据状态，修正收益空值语义。
3. 完成分类规范化。
4. 合并资产配置与再平衡。
5. 使用 Sheet 和结构化行编辑器替代 JSON 表单。

### 第二阶段：收益走势

1. 增加净资产走势图。
2. 将 Snapshot 明细改为可展开区域。
3. 完成图表的空状态、错误状态、键盘与视觉验收。

第一阶段完成后页面即可独立交付；第二阶段不得阻塞正确性修复。

## 验证策略

### 确定性验证

- 分类规范化单元测试覆盖大小写、中文别名、重复别名合并和未知旧值。
- UI contract 测试覆盖“全部账户”、模式切换后的账户过滤和无效账户重置。
- 指标测试覆盖 0、1、2 个 Snapshot，以及 XIRR 可解、不可解和 partial Snapshot。
- 配置区测试覆盖无目标、有目标、行情缺失和 allocation 失败。
- Sheet 测试覆盖新增、删除、重复分类、权重合计、未保存关闭和保存失败保留输入。
- Query 测试确认 key 包含正确范围，目标保存后只失效相关查询。
- 执行 Desktop 定向测试、typecheck、lint/build 中与修改范围相称的检查，以及 `git diff --check`。

### 视觉与运行时验收

- 在真实 Desktop 页面分别验证宽屏和窄屏布局。
- 验证实际组合、影子组合、全部账户、单账户四类切换路径。
- 验证空历史但有持仓时，页面不再出现互相矛盾的“暂无数据”。
- 验证键盘可以完成范围切换、打开 Sheet、编辑目标、保存和关闭确认。
- 第二阶段单独验证图表 tooltip、数据点密集场景和明细展开行为。

## 验收标准

1. 页面主流程符合“选择范围 → 看收益 → 看配置偏差 → 调整目标”。
2. 历史为空但配置存在时，不显示页面级“暂无数据”。
3. Snapshot 不足时不显示 `TTWROR 0.00%`，XIRR 显示明确原因。
4. `etf`、`ETF` 等同义分类不会生成相互矛盾的配置与再平衡结果。
5. 用户无需编辑 JSON 即可新增、修改和保存目标配置。
6. 无效目标无法提交，保存失败不会丢失草稿。
7. 实际/影子模式与账户选项始终一致，“全部账户”可明确选择。
8. 页面继续明确说明再平衡结果只是建议，不会自动下单。
9. 第一阶段不引入新的收益计算公式；第二阶段图表只可视化现有 Snapshot。
