# AI 实验自动完成

## 目标

实验创建后自动完成候选生成、开发与验证评估、封存测试和结果揭示。用户查看完整结果后决定是否采纳正式策略。Desktop 和 Mobile 使用同一执行与展示合同。

## 行为合同

- AC1：生成阶段结束后，将全部开发、验证均有效的去重候选按候选编号锁定，自动测试基线及这些候选；不自动指定采纳候选，不自动创建正式策略。没有合格候选时保留具体失败终态。
- AC2：测试批次和冻结输入在首次访问测试数据前持久化。结果统一揭示，测试数据不进入模型反馈；已开始过的历史批次保留原集合及原提前选择。技术重试只使用已有锁定事实，复用已完成部分。
- AC3：进程在候选阶段结束与测试领取之间退出时，后台恢复器能接续尚未访问测试的实验。领取使用状态与 attempt 条件，进程恢复与重复请求不能重复生成候选或覆盖终态。技术失败保存具体原因并暂停等待重试，不无限自动消耗预算。
- AC4：回测预算预留完整最坏路径：三次基线切分，加每个模型每轮最多一次候选的三次切分。零值不限额语义、总时长及已有预算保持生效，不扩大用户额度。
- AC5：详情、列表、旧结果入口及 Mobile 展示自动运行阶段、完整候选结果及正式采纳入口。正常运行无需选择批次或预选采纳；技术失败保留重试与取消操作。已有未开始测试的等待实验自动接续，已开始过的批次沿用原恢复方式。

## 所有权与实施边界

StrategyOptimization 的封存执行收敛到独立编排模块，主服务保留生成编排和采纳。Schemas 与 API client 提供按实验身份接续／重试的接口；旧显式 finalize 请求仅保留历史客户端兼容，不作为新界面流程。数据库字段和结构沿用已有合同。

旧等待状态仍可作为领取前的短暂持久化阶段，展示为正在准备测试；带技术失败原因时展示中断。自动接续不改变已完成、已失败、已取消实验，也不重跑已揭示测试。

验证先使用单元和隔离 PostgreSQL，再做四宽受控浏览器与正式运行态核验。开发阶段的真实来源、实际 AI 调用和用户正式采纳不作为受控验收输入。部署遵守当前结构与依赖兼容门禁；当前工作区若已有必须同步的增量结构，先核对清单，再通过已有保留数据升级入口备份、恢复副本演练和单事务执行，不执行开发重建，不将结构同步当作其他产品功能的准入证据。

本规格接续[实验测试候选选择](../archive/specs/2026-11-12-experiment-test-selection.md)。任务：[已完成清单](../archive/tasks/2026-11-12-automatic-experiment-completion.md)，证据：[验收记录](../archive/evidence/2026-11-12-automatic-experiment-completion.md)。

## 失败后的人工重试

失败后的人工重新执行遵循[原地失败重试](2026-11-12-experiment-manual-retry.md)：保留实验身份与累计用量，并明确记录本次恢复授权。原实验的失败终态不会由后台自动重启；测试已锁定时仍使用原封存测试恢复入口。

只有全局来源目录更新时，冻结父输入的重新准入遵循[冻结行情重新校验](2026-11-12-experiment-retry-catalog-revalidation.md)；实际来源变化、撤销及真实预热不足继续阻断。

## 运行态构建前提

Server 的竞技场 HTTP 集成测试需要共享 API client。该依赖应声明为 Server 开发依赖，并使用包入口导入，使正式 `server... build` 在干净镜像中先构建客户端；生产依赖方向保持不变。不得依赖宿主已存在的 `dist`，也不得跳过测试编译掩盖缺失依赖。
