# 通知 Provider 路由与交互 Spec

## 背景与问题

风险提醒和定期入账提醒的通知策略把 `feishu` 写成固定渠道。投递服务虽然可以在 Provider 未配置、被停用或缺少凭证时跳过入队，但上游语义仍表现为“默认飞书”，桌面端也没有说明当前实际投递到哪个 Provider。定期入账链路还会把空入队结果误报为已排队。

## 目标

- 通知路由由当前已启用、凭证有效且已有投递适配器的通知 Provider 配置决定，上游业务不指定飞书。
- 没有可投递 Provider 时不创建投递记录，也不报告已排队。
- 风险中心明确展示当前通知去向；没有可用 Provider 时说明风险事件仍会保留，并提供配置入口。

## 非目标

- 本次不新增飞书之外的通知适配器。
- 不改变风险规则判断、风险事件写入、冷却、重试、静默时段或失败隔离语义。
- 不迁移或删除历史通知投递记录。

## 现状与约束

- `ProviderConfig` 以 `type = notification`、`enabled`、优先级和加密凭证保存通知 Provider。
- 当前唯一已有投递适配器的渠道是飞书，兼容既有飞书与 Lark 名称别名。
- 通知投递必须与风险事件和定期入账实例写入隔离；没有通知 Provider 不能阻止业务记录落库。
- 桌面端使用 TanStack Query，并复用现有 shadcn/ui 组件和原子类。

## 设计方案

### Provider 驱动路由

投递服务从 Provider 配置解析当前路由：只接受已启用、类型为通知、凭证可解密且非空、并有已实现适配器的配置。同一渠道存在多个候选时按优先级和名称选择第一个；未来出现不同已支持渠道时可分别形成路由。

业务通知策略只保留冷却、最大尝试次数、静默时段和严重级别旁路等业务规则，不再声明具体渠道。

### 状态语义

入队返回实际创建或更新的投递结果。空数组表示当前没有可投递 Provider。调用方只有在结果非空时才可报告 `notificationQueued = true`；异常和空路由均不得回滚业务记录。

### 桌面交互

通知模块提供只读的当前路由摘要，不包含凭证。风险中心使用 TanStack Query 读取摘要：

- 有路由时，通知页说明实际通知会发送到哪些 Provider；
- 无路由时，使用状态提示明确说明不会发送外部通知、风险事件仍会保留，并提供“配置通知 Provider”入口；
- 路由读取失败时，不把未知状态误报为未配置，改为提示暂时无法确认。

## 对外行为或接口变化

- 新增只读接口 `GET /notifications/routing`，返回 `routes`，每项包含 `channel` 与 `provider`。
- `NotificationPolicy` 不再接受 `channels`；渠道由 Provider 配置解析。
- 自动化日报摘要不再返回静态的 `channels: ['feishu']`，避免把内容摘要误表示为真实投递配置。
- 定期入账物化结果中的 `notificationQueued` 改为准确反映是否实际产生投递记录。

## 数据、状态或兼容性影响

- 不修改数据库 Schema。
- 新投递记录的 `provider` 在入队时即保存被选中的 Provider 名称；`channel` 保存归一化渠道。
- 历史记录保持可读；典型旧值 `provider = feishu` 仍可按现有配置解析。

## 测试策略

### 关键可观察行为

- 未配置、停用、空凭证或无适配器的 Provider 不产生投递。
- 已配置飞书或 Lark 别名时按优先级选路并产生投递。
- 空入队结果不会被报告为已排队。
- 风险通知页区分已配置、未配置和路由状态未知。

### 优先测试层级

- NotificationService 单元/运行时测试验证路由解析、入队和派发。
- 定期入账服务测试验证 `notificationQueued`。
- Desktop 组件测试验证通知页文案和配置入口。

### 可复用的现有测试入口

- `apps/server/test/notification-runtime.test.ts`
- `apps/server/test/notifications/services.test.ts`
- `apps/server/test/cash-plans/recurring-cash-deposit.service.test.ts`
- `apps/desktop/test/risk-center-interaction.test.tsx`

### 需要新增的测试入口

无，复用现有入口。

### 关键边界与回归场景

- Provider 配置损坏时不得在入队阶段抛出凭证内容。
- 多个同渠道 Provider 不得重复发送。
- 路由查询失败不能显示为“未配置”。

## 风险与备选方案

- 直接在桌面端从 Provider 列表推导路由会复制服务端适配器支持规则，因此采用服务端只读路由摘要。
- 当前只有飞书适配器，因此配置其他通知 Provider 仍不会形成可投递路由；界面以实际路由为准，不以类型或能力声明冒充可用。

## 未决问题

### Blocking

无。

### Non-blocking

- 后续新增不同通知渠道时，默认对每个已支持渠道选择一个最高优先级 Provider 并同时投递；本次仅有飞书渠道，当前行为不受影响。

## 验收标准

- AC1：业务通知不再静态指定飞书，实际路由由可投递的通知 Provider 配置决定。
- AC2：没有可投递 Provider 时不创建投递记录，也不报告通知已排队。
- AC3：风险中心能展示当前实际通知 Provider；未配置时明确说明不会外发并提供配置入口。
- AC4：路由状态读取失败时界面显示未知/重试语义，不误报为未配置。
- AC5：既有风险事件、定期入账、冷却、重试和历史投递语义保持不变。
