# 回测结算日历覆盖

## 问题与证据

`backtest-dependency-price.ts` 的 calendar 数据集沿用行情范围，截止 runConfig.endDate；`backtest-snapshot-v3-dependencies.ts` 再强制核对这一截止日。执行模型的 exchange 分别允许 sellableAfterTradingDays、saleReinvestableAfterTradingDays 为 0–30。运行器在期末成交时调用结算日期计算，冻结日历不足会抛出“交易日历覆盖不足，无法计算结算日”。

`v3-split-mapping-snapshot.test.ts` 已实际复现：快照构建成功，运行失败。将合成日历事实扩展到后续日期后运行通过。该扩展仅是测试输入补全，未修复生产依赖计划。

## 必须满足的行为

1. 新建完整快照时，执行日历须覆盖最后可能成交日之后模型所需的结算交易日。只扩展日历，不扩展策略决策、价格行情、事件经济窗口或估值输出。
2. 所需交易日数来自运行窗口内适用的冻结模型段：exchange 取买入可卖与卖出可再投资天数的最大值。不能以固定 T+1 替代模型。当前完整 V3 不支持 NAV，不能凭本修复声称 NAV 结算已覆盖。
3. 日历请求可使用有上限的保守自然日候选范围，但完整性必须按返回的冻结日历实际交易日验证；长假或供应商截断导致交易日不足时，必须在 finalized 前失败，不能把自然日缓冲当作已证明的交易日。
4. 数据请求范围、响应覆盖、事实范围及证据行一致，并纳入快照身份。离线重放不补取日历。
5. 模型为 T+0 时不引入无必要的后续日历要求。多段模型按运行窗口交集取最大需求，不采用窗口之外的未来规则。

候选请求策略 `settlement-calendar-v1`：T+0 保持结束日；其他情况增加 `最大结算交易日数 × 3 + 14` 个自然日（当前模型上限 30，对应最多 104 日）。这是有界请求预算，不是交易日保证；必须使用返回日历逐日验证足够数量的后续交易日，遇到未知覆盖立即拒绝。新建完整快照已接入该策略，旧无标记快照保持原请求范围。

## 兼容性

DSA 日历 HTTP 端点必须独立校验计划范围：start 不晚于 dataAsOf 日期，end 可晚于该日期但最多 104 个自然日，且必须处于实际安装日历包覆盖范围。未来计划日历不是未来行情；行情与其他经济事实仍使用原有 end 不晚于 dataAsOf 规则。该修复不证明包内容的历史发布可见性，R01.10 的独立证据要求继续保留。

新完整快照的元数据冻结 `settlementCalendarPolicy=settlement-calendar-v1`。基础依赖计划保留原始运行范围，实际日历请求由冻结策略扩展；创建和离线校验共用请求生成器。旧快照缺少该标记时按其既有冻结合同校验和重放，不在读取旧快照时扩大期望请求范围、修改内容哈希或重新生成证据；旧快照确实无法支持原执行时，保留明确缺失错误。未知策略版本必须拒绝。

共享策略、V2/NAV 原始路径和既有 G-Legacy 验收不因该补丁变更。不能用跳过期末成交、修改为 T+0 或删掉结算事件掩盖缺口。

## 验收

- 期末成交的 T+1/T+2、周末和长假均有真实冻结日历支持并可离线重放。
- T+0、窗口外模型段、空/截断/未知日历、篡改结算策略版本均有明确结果。
- 旧完整快照保持原身份和可重放行为；缺失本就需要的日历时继续报错。
- 定向测试、Server 类型检查、快照/执行相关包回归通过后，再考虑目标运行时更新。
