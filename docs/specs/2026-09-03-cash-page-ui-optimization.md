## 目标

现金页面的阅读顺序固定为“现金总览 → 待结算 → 最近流水 → 定期入账”。优化重点是减少重复 Card 和无效空白，让用户优先看到可用现金、待结算资金和最近现金变动。现金入账、账户间划转、现金快照和定期入账的业务行为、权限、数据口径与 Ledger 写入行为保持不变。

## 非目标

- 不修改现金 Ledger、Snapshot、Settlement 领域模型或结算规则。
- 不修改多币种折算逻辑，不在缺少可靠汇率时合并不同币种。
- 不修改现金相关 API 和表单业务字段。
- 不重构其他资产页面、全站 Card、Button、Badge 或列表组件。

## 页面结构

现金页面包含四个层级：

1. 页面 Header：现金入账为唯一 Primary；账户间划转为 Secondary；现金快照收进 More Menu。
2. 现金总览：可用现金、待结算应收、待结算应付三个摘要项。Desktop 三列，Tablet 可 2+1，Mobile 纵向展示。
3. 待结算：按明确的结算时间升序展示轻量列表；短日期、类型、币种和备注位于信息区，金额右对齐，应收带 `+`、应付带 `-`，状态弱化展示。
4. 最近流水：默认只展示最近 5 条已结算现金流水，提供页内“查看全部”展开；单条流水使用 List Row，备注作为辅助行。
5. 定期入账：待确认记录优先，随后展示计划；使用轻量 Section/List，不使用多个重型独立 Card。

## 数据与展示约束

- 可用现金按币种展示；只有存在可靠折算值时才展示本位币合计。
- 待结算只使用账本中明确的未来结算时间，不推测缺失时间。
- 现金流水和待结算的备注存在时展示，不生成空占位；长备注截断或折行，不得挤压金额。
- 已结算状态优先使用弱化文本或轻量 Badge，金额本身是主要视觉信息。
- 空状态、加载失败、部分数据和无汇率状态沿用现有错误反馈，不改变数据计算。

## 响应式约束

- Desktop（`>=1024px`）：总览三列，列表日期/信息/金额结构稳定，金额右对齐。
- Tablet（`768px~1023px`）：总览允许换行，Header 操作不溢出。
- Mobile（`<768px`）：摘要纵向或窄屏布局，列表可拆成两行，不依赖横向滚动表格。
- 长备注、长账户名称和操作入口不得造成明显横向溢出。

## 验收标准

- AC1：页面阅读顺序为总览、待结算、最近流水、定期入账。
- AC2：Header 只有现金入账使用 Primary，账户间划转为次级操作，现金快照仍可发现并使用。
- AC3：单币种总览紧凑展示可用现金、待结算应收、待结算应付和笔数；多币种不错误合并。
- AC4：待结算按结算时间升序，只展示明确未来时间；应收/应付金额分别使用 `+`/`-`，备注不挤压金额。
- AC5：最近流水默认最多 5 条，提供“查看全部”，单条不使用独立 Card，备注作为辅助行。
- AC6：定期入账与待确认位于同一轻量 Section，创建、确认、跳过和恢复行为保持可用。
- AC7：无余额、无待结算、无流水、无计划、加载失败、部分数据和无汇率均有清晰且紧凑的展示。
- AC8：Desktop、Tablet、Mobile、Light/Dark Mode 下无明显溢出，金额和日期可快速扫描。
- AC9：现金入账、账户间划转、现金快照、定期计划创建/确认及数据口径与改造前一致。

## 实施假设

- 现金快照的低频入口采用现有 DropdownMenu 的 More Menu，不新增导航。
- 当前没有独立现金流水页，“查看全部”采用页面内展开，不新增路由或 API。
- 现有事件和估值 Query 已提供本次展示所需数据，仅在前端组合和排序。
