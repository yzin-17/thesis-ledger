# 交易与成交记录系统 Spec

## 背景与问题

当前 ThesisLedger 已使用 `LedgerEvent` 作为资产变化事实源，并由此重建 Position、现金和投资复盘候选。但现有产品仍以“当前持仓”为主要录入对象，成交修正、历史基线对账、完整交易周期、部分减仓复盘和多币种结算尚未形成统一契约。

本 Spec 的 V2 Ledger 语义覆盖旧版 Position Entry 文档中关于 `Adjustment` 写入的描述；旧文档仅保留页面与账户模型背景，当前事件类型以本 Spec 及其子 Spec 为准。

现有实现还存在以下约束：

- Position、Ledger 和估值使用 `Asset.symbol`，不能直接改用 `instrumentId` 形成第二套资产身份。
- 旧 `correctionOf` 只保存弱引用，且历史含义不一致，不能直接解释成通用修正协议。
- Journal 当前按每次卖出形成候选，与“持仓从 0 开始并最终回到 0”的完整 Trade 不是同一粒度。
- Position 已处理送股、拆股、合股，新的 Trade Projection 也必须处理，否则剩余数量无法一致。
- 当前领域计算部分使用 JavaScript `number`，不足以承担跨币种费用分配和多次部分卖出的精度要求。

## 目标

- 保持 LedgerEvent 为唯一经济事实源，Position、Trade 和 Cash 均为可重建读取模型。
- 支持真实成交录入、修正、作废、恢复、历史补录、Baseline 对账和确定性重建。
- 同时表达完整交易周期与每次减仓切片，并为 Journal 提供统一事实来源。
- 保证成本、费用、税费、数量和现金在高精度计算下守恒。
- 支持实际账户与影子账户、多币种现金、待结算资金和独立汇率折算。
- 为历史迁移、影子计算、分阶段切换和最终一致性 Review 提供明确门槛。

## 非目标

- 券商下单、订单簿、限价单、撤单和部分成交订单状态。
- 做空、融资融券、期权和期货。
- 场外基金申请中、待确认和撤销流程；第一阶段只记录已经确认的申购或赎回结果。
- CSV 成交导入、券商自动同步和长期并存的双投影兼容路径。
- 证券转入与转出；第一阶段遇到此类历史变化时使用持仓观察并标记证据不完整。
- Trade 人工合并、拆分或直接编辑。
- 将 AI 用于自动决定 Baseline 对账或写入交易事实。

## 现状与约束

- 账本、持仓、行情和估值继续以 `Asset.symbol` 为关系键；Instrument 只用于搜索和识别。
- 说明性文档使用中文；Spec 与任务文档必须成对维护。
- 业务数据库角色不得更新或删除 LedgerEvent；历史修正只能追加新事实版本。
- 用户补录历史数据时允许证据不完整，但不允许静默制造负持仓、虚假成交或自动充值。
- 实际账户与影子账户共享模型，但交易性质、查询、统计和复盘不能混算。

## 设计方案

### 1. 账本信封与类型化载荷

LedgerEvent 使用统一不可变信封和类型化 JSONB payload：

- `factId` 标识稳定的经济事实，`eventId` 标识该事实的一次追加版本。
- 信封记录账户、事件类型、账户级 Ledger Revision、业务发生时间、时间精度、不可变排序键、来源类别、具体渠道、操作者和审计信息。
- 账户、`Asset.symbol`、事件类型和经济时间等高频查询键使用独立索引列，并与 payload 保持一致。
- 类型化载荷按版本迁移到当前规范；运行时不长期保留旧载荷兼容分支。
- 同一账户的账本写入串行化。状态型命令必须携带 `expectedLedgerRevision`，普通新增成交只要求幂等键。

修正限定为单链操作：

- `REPLACE`：以新版本替代当前有效版本。
- `VOID`：使当前经济事实无有效版本。
- `RESTORE`：在作废节点后恢复为明确载荷。

修正只能操作链末端，原因、操作者和来源必填。幂等范围为账户、具体来源渠道和外部编号；同内容重放返回原结果且不增加 Ledger Revision，不同内容进入冲突处理。

### 2. 时间、结算与精度

- 成交时间与结算时间分开；Trade 和 Position 按成交时间变化，Cash 按结算时间变化。
- 来源只有日期时保存来源时区并标记日期级精度，不伪造时分秒。
- 历史数据缺少来源时间精度或来源时区时显式标记为 `UNKNOWN`，不得使用服务端写入时间或 `UTC` 冒充来源时间。
- 来源业务时间完全未知时，`UNKNOWN` 事件的 `occurredAt` 保持为空，仅按 `economicOrderKey` 和 `eventId` 做确定性排序。
- 同一业务发生时间使用账户内统一、可在既有事件之间插入的排序键；来源原始序号作为证据另存。
- 缺少结算时间时使用版本化市场规则推定并标记 `INFERRED`；无法推定时保持 `UNKNOWN`。
- 数量、价格、费用、成本和收益使用十进制领域类型，API 统一传十进制字符串。
- Asset 或市场能力提供数量步长、数量精度、最小报价单位和价格精度；能力缺失时使用通用高精度校验并标记未验证。

### 3. Historical Baseline 与导入

一次截图或完整持仓校准创建 Baseline Observation Batch：

- 批次记录账户、业务观察时间、采集时间、写入时间、来源及 `FULL / PARTIAL` 范围。
- 每个资产生成独立 Baseline Observation 事件并共享 `batchId`。
- `FULL` 中缺失的已有资产可形成数量 0 观察；`PARTIAL` 只影响明确出现的资产。
- 多次观察作为不同时间检查点保留，不覆盖旧观察。

Trade 内使用独立 Baseline Component，不把基线伪装成 BUY Entry Leg。基线只保存来源提供的平均账面成本价，费用包含情况可以未知；基于基线计算的收益必须标记为估算。

Baseline 对账遵循以下规则：

- Baseline 是对应时点的权威数量和成本观察。
- 历史成交只纳入对账历史一次，并从发生时间向后重放所有检查点。
- 部分覆盖后的剩余数量和剩余成本分别等于 Baseline 总量减已覆盖实际量，保持数量和成本守恒。
- 覆盖关系由 `BASELINE_RECONCILIATION` 事件保存。系统只能使用确定性规则推荐候选，用户确认后才生效。
- 余额观察为 0 可以结束持仓生命周期，但缺少 SELL 时不能生成平仓时间、退出价和价差收益。

批量导入先进入单账户 ImportDraft。Draft 保存不可变原始证据引用、内容哈希、解析器版本和来源行 ID；数量、价格和收益率等识别结果以十进制字符串保存，提交版本冻结。合法选中项在账户锁内原子提交，孤立卖出、幂等内容冲突和无法解释的行继续留在草稿。`partial` Draft 可从未提交行创建后续 Revision；已提交 Revision 的行不可修改，后续 Revision 只携带未提交行，完成判定合并历史与当前 Revision 的提交范围。

### 4. Trade Projection

Trade 始终按单一账户和 `Asset.symbol` 划分。数量从 0 变为正时开启周期，回到 0 时结束周期。生命周期状态与退出进度、结束证据分别建模：

- 生命周期：`ACTIVE / ENDED`。
- 退出进度：未退出、部分退出、全部退出。
- 结束证据：真实成交平仓、余额观察结束或其他证据不足原因。

发生过卖出且仍有仓位时保持“部分平仓”，后续加仓只增加 Entry Leg，不重开周期。

物化读取模型至少包含：

- Trade Projection。
- 真实 Entry Leg。
- Baseline Component。
- Corporate Action Adjustment。
- Close Slice。
- Close Allocation。
- Dividend Attribution。

每个账户使用不可变成本策略版本。现有账户迁移为移动加权平均成本法；一个 Trade 始终使用开仓时的策略版本，后续策略变更只影响新 Trade。

- 先进先出成本法按 Entry Leg 或 Baseline Component 实际消耗顺序生成 Close Allocation。
- 移动加权平均成本法按各来源剩余数量比例生成 Close Allocation。
- 同一资产的后续 Baseline 是余额检查点；只物化未解释差额，成本按观察总成本减已知成交剩余成本重估，不能把绝对余额再次累加。
- 毛收益只表示买卖价差；净收益扣除分配到本次减仓的买入费用及本次卖出费用。
- 费用使用类别、金额、币种和说明组成的明细数组。
- 中间计算不按展示精度舍入；完全平仓时最后一个 Close Slice 承接尾差。
- 默认收益率为已实现净收益除以对应买入成本和买入费用，不混入未实现收益。

送股、拆股、合股作为独立调整记录。拆股和合股使用 `fromUnits / toUnits`；分红作为独立投资收入归属 Trade，不混入价差收益。

### 5. 多币种 Cash 与 FX

- `Account.currency` 改为账户本位币，不限制成交或现金币种。
- Cash 按账户和币种分别投影，并区分已结算余额与待结算应收/应付。
- T10 首阶段在账本写入事务内，以账户下一代 `Projection Generation` 原子替换 Position、Trade 及其子表、Cash 余额和待结算明细；未来 `settledAt` 在到期前计入待结算，缺失 `settledAt` 的现金变动按已结算处理。
- 现金证据不完整时允许出现负余额，但必须标记缺失资金事件，不能自动生成充值或解释为融资。
- 原币 Trade 是核心投影；本位币 Trade 和组合汇总由独立 FX Conversion View 生成。
- 每笔成交、费用、税费和分红按各自经济发生日汇率折算，并保存汇率来源和版本。
- 缺少汇率不阻止原币投影，本位币结果显示不可用或部分可用。

### 6. 产品与 Journal

账户数据使用三个同级页签，默认打开“成交记录”：

1. 持仓：展示 Position，并提供次级“校准持仓余额”。
2. 成交记录：主入口“录入成交”，默认显示当前有效版本，可展开修正链；通过筛选查看其他账本事件。
3. 现金：按币种展示已结算余额和待结算项。

Trade 列表、详情和分析位于投资组合“交易”页签，不放在账户数据录入层。Trade 只读，详情顶部提供完整交易周期复盘，每个 Close Slice 提供减仓复盘。

Journal 不再自行从 Ledger 拼装交易：

- 完整 Trade 和 Close Slice 是两个明确复盘对象。
- 周期统计默认按真实 SELL 结束且成本充分的完整 Trade 计算。
- Close Slice 单独形成退出执行统计，不混入完整交易胜率。
- 基线证据不完整但生命周期已结束的 Trade 可受限复盘，依赖缺失事实的指标显示证据不足。
- 现有逐次卖出候选按 SELL LedgerEvent ID 映射到 Close Slice；无法唯一匹配的记录保留为 legacy。

### 7. 稳定引用与查询

- Trade ID 只保证当前有效输入和算法版本下可重复生成，不承诺历史补录后永不变化。
- Journal、备注和 AI Review 保存账本证据、Ledger Revision、投影版本、FX 证据版本和 Trade Projection 指纹。
- 相关输入变化时旧结果标记为需要重新确认；无关账户或标的变化不使其过期。
- 旧 Trade 链接按所保存账本证据尝试解析到当前唯一 Trade；无法唯一解析时展示旧快照，不做相似度猜测。
- Trade 列表游标绑定账户级 Projection Generation；世代变化时要求刷新，避免重复或漏项。
- 正常页面读取当前物化投影；审计可按 Ledger Revision 即时重放相关资产。

## 对外行为或接口变化

- 新增专用成交命令，不再让普通表单直接提交任意 LedgerEvent。
- 新增成交替代、作废和恢复命令；跨账户更正使用“原账户作废 + 目标账户新建”的双账户原子命令。
- 新增 Baseline Observation、Baseline Reconciliation 和 ImportDraft 审核提交命令。
- 新增有效事件列表与修正链审计读取能力。
- 新增 Trade 列表、详情、Close Slice 和账本证据解析接口。
- Trade、Cash 和金额类接口使用十进制字符串，并返回数据完整度、来源和投影版本。
- 实际账户与影子账户必须显式区分，查询键和统计不得混用。

## 数据、状态或兼容性影响

- 旧 `correctionOf` 在完成新字段回填并通过校验后，由独立收缩 migration 删除；不导出审计快照，也不迁入 metadata。
- 旧 `ADJUSTMENT` 按 `metadata.kind` 转换为专用事件；未知语义阻断迁移。
- 现有账户创建移动加权平均成本策略初始版本，并从账户最早 LedgerEvent 起生效。
- 原有 Position、Cash 和 Journal 候选在切换前保留，用于影子结果比较；切换完成后删除旧独立计算路径，不建立兼容重导出。
- 当前任务验收范围限定为本地环境：本地 Docker 临时隔离数据库、Compose 运行态和应用内浏览器即可作为证据；不得修改开发持久卷或原始事实来配平差异。
- 正式发布环境的数据副本、备份恢复、性能/并发、在线 FX、发布切换和旧镜像回滚不属于当前 Spec 范围，不作为本地任务完成条件；未来发布时另立门禁。

## 风险与备选方案

- 历史基线成本口径未知会产生估算收益；通过证据完整度和统计排除规则控制，不自动推断费用。
- 历史补录可能改变 Trade 边界；通过账本证据、投影指纹和旧快照保留可追溯性。
- 物化投影增加写入事务成本；第一阶段按账户串行化并只重建受影响资产，性能不足时再基于同一契约优化。
- 多币种汇率缺失会阻断本位币汇总；保留原币结果并明确不可用状态，不使用当前汇率替代历史汇率。
- 独立收缩 migration 删除旧 `correctionOf` 会永久失去弱关联线索；这是已确认的数据迁移选择。

## 未决问题

无。实现范围或外部行为发生变化时，必须先更新本 Spec 和对应子 Spec，再同步任务文档。

## 验收标准

1. LedgerEvent 不可直接更新或删除，修正链、幂等重放和账户 Ledger Revision 行为确定。
2. 同一账户并发写入不会产生超额卖出、重复成交或不同步的 Position、Trade、Cash。
3. 相同有效事件、策略和算法版本重复投影得到相同结果。
4. Position 数量等于所有 ACTIVE Trade 的剩余数量；公司行动后仍保持一致。
5. Close Allocation 的数量、成本和费用之和与 Entry Leg、Baseline Component 和原始费用守恒。
6. Historical Baseline 可部分、完整和跨检查点对账，不与历史成交重复计入。
7. 实际账户与影子账户、多账户和多币种数据不会混算。
8. 原币结果在汇率缺失时仍可用，本位币结果明确显示不可用或部分可用。
9. 账户数据默认进入成交记录，并提供持仓、成交记录、现金三个同级页签。
10. 投资组合提供 Trade 列表和详情，并分别支持完整 Trade 与 Close Slice 复盘。
11. Journal 与 Trade 页面使用同一 Trade Projection，不再存在第二套交易拼装结果。
12. 旧 Journal 候选完成确定性迁移或明确标记 legacy，旧复盘可判断是否过期。
13. 影子投影差异全部分类，迁移缺陷和算法缺陷清零后才能切换统一读取模式。
14. 单元、属性、数据库迁移、并发、浏览器和运行时验收分别记录，不以确定性测试替代真实运行验收。
