## 2. TTWROR：尊重现金流边界

精确时间加权收益须由有证据的现金流前后估值分段连乘，或由合同明确且满足前提的边界资金流规则计算。初始 100、追加 100 后资产上涨 10%、末值 220，应得到 10%，不能计算成 20%。同样初末值但流量发生在收益之后可以得到不同收益，不能仅凭净流量区分。

默认不引入另一种近似指标来冒充精确 TTWROR。现存日级快照不足以识别中途现金流边界时，保持指标不可用并给出原因，其他可独立计算的指标仍可读；无外部流量的合法区间保持原行为。需要新增采样/持久化才能补齐边界时先原位拆分相应实现叶，不在公式修复中隐式增加自动任务或重写旧快照。

纯计算输入可在现金流发生时点提供 `flowBoundary: {before, after}`，该点 `value` 必须等于流后估值，且流后减流前等于 `externalFlow`；各段以流前/上一流后估值连乘。没有该证据的非零现金流直接不可用；`externalFlowCount` 保留零净额但存在现金流的区别。Server 日级 summary 只提供事件计数，不虚构边界。独立 `ttwrorReason` 与 `xirrReason` 返回各自原因；一个指标不可用不阻断另一个。

沿用现行账户/组合范围和 [外部现金流分类](../../apps/server/src/performance/performance-ledger-flow.ts)；内部划转不能重复计外部流量。历史 FX 缺失、部分估值及零/非法分母不补零、不按当前 FX 回填。

## 3. XIRR：有界求解与准确失败分类

固定现有年长/日期基准，排序、合并同日流量并验证有限数与正负流量；求解限定 `rate > -1`，迭代与搜索有上限。对导数退化、跨定义域、非有限中间量及 Newton 失败使用有保护的求根方法，输出以残差而非仅迭代步长验收。

2025-01-01 投入 100、2026-01-01 回收 10 存在接近 −90% 的有限解；精确数值按当前 365.25 天年长核验，不无提示切换成 365 天。一般非传统流量可能有多解，固定根选择规则并披露歧义；未证明唯一或无解时不能把搜索失败标为数学无解。已检测多解、输入无效和有界不收敛须有可解释原因，不返回 NaN/Infinity/假零收益。

日期保留原毫秒时间差，按同一时间戳合并而不截断日内时分秒。归一化金额后在 `log(1+rate)` 的有界范围内搜索并验证回代残差；365.25 天口径不变。仅单次现金流符号变化接受唯一有限根；多次变化时，检测到多根明确拒绝，单个候选也不推断唯一，返回根歧义。有限搜索无候选只报告搜索不足。`guess` 校验有限且大于 −1，不作为跨定义域迭代的起点。

## 4. 再平衡：保留全部资金来源与去向

比较集合采用规范化后当前类别与目标类别的并集；当前存在而目标未列的类别按目标 0 表达，目标存在而当前未持有的类别按当前 0 表达。股票/现金各 500、目标 `{stock:1}` 必须同时输出股票 +500 和现金 −500。

不改变持仓/现金纳入范围、FX 合并开关或已有类别键。完整同币种且无外部资金时，未舍入差额总和为 0；按展示精度舍入后应明确处理尾差或披露尾差，不伪造额外入金。缺估值/FX 时暂停完整比例和再平衡建议，保留已知金额。仅提供建议，不下单。

## 5. 目标保存：原子且并发安全

校验、版本分配、新目标创建与旧目标替换必须形成同一原子发布结果。创建失败后旧目标仍有效；同一现行 scope/account 身份内并发写入不得产生重复版本、多个 active 或零 active 的中间可见状态。不能仅加一层事务而忽略版本竞争及 nullable accountId 的唯一性语义。

PFC0 先核对现有表约束和调用方，确定数据库约束与串行化策略；保留现行目标身份和客户端合同，不顺带改成按模式另一套目标系统。若引入新结构，使用新增 migration，保留升级、冲突预检和回退兼容单独验收，不清理已有目标来迁就唯一键。

当前保存服务采用 `scope + accountId|null` 身份的事务级 PostgreSQL advisory lock，再在同一事务内停用旧版本、读取最高版本并创建新版本。覆盖现有服务写入路径的竞争与回滚，不新增 Schema/migration；不声称能约束绕过此服务的任意直接写表行为。真实隔离 PostgreSQL 验收仍是 PFC1 必要条件。
