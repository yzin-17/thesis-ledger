# 策略实验工作台交互优化规格

## 背景与问题

当前 Desktop“策略实验”页面把新建策略、编辑 `Strategy Schema JSON`、策略版本、回测任务和回测结果纵向堆叠在同一页面。完整 JSON 编辑器长期占据主要视区，策略版本与任务列表需要滚动较长距离才能看到，页面首先暴露机器契约，而不是用户的实验流程。

现有交互还存在以下语义和数据关联问题：

- 页面标题为“新建策略”，提交按钮却是“保存新版本”，没有区分首次创建与基于历史版本迭代。
- “排队回测”从策略行选择最新版本 ID，却从页面全局 JSON 草稿读取 Schema 和行情标的，可能使任务版本与准备行情时使用的配置不一致。
- 回测区间 `2025-01-01` 至 `2025-01-31` 和初始资金 `100000` 固定在前端逻辑中，用户无法在开始回测前确认或修改。
- 回测任务主要展示截断 UUID 和英文状态，不利于识别“哪条策略的哪个版本正在运行”。
- 任务已通过 TanStack Query 对非终态任务每 1.5 秒自动轮询，顶部“刷新策略任务”却仍作为高强调操作出现。
- 回测结果继续追加在长页面底部，选择任务后缺少聚焦的结果查看上下文。

服务端已经提供创建策略、创建新版本、列出策略、排队、运行和取消回测的接口。本任务应优先修正前端信息架构、状态管理和接口使用，不通过新增后端能力掩盖交互问题。

## 目标

- 将页面改造为以“策略库”和“回测任务”为核心的管理型工作台，首屏优先展示可操作对象而不是完整 JSON。
- 明确区分“创建策略”和“保存为新版本”，历史版本保持不可变。
- 使用宽 `Sheet` 承载策略创建与版本编辑，提供常用配置表单和高级 JSON 两种编辑方式。
- 使用居中 `Dialog` 承载回测配置和结果详情，使任务版本、回测参数和结果上下文保持聚焦。
- 回测必须绑定用户明确选择的策略版本，并从该版本保存的 Schema 读取行情标的，禁止读取无关的编辑器草稿。
- 在开始回测前允许配置回测起止日期与初始资金，并将“排队”和“运行”合并为一个面向用户的“开始回测”动作。
- 用策略名称、版本号、中文状态、必要进度和时间信息替代主要 UUID 展示。
- 继续使用 TanStack Query 管理查询、轮询、Mutation 和失效，不恢复手工请求状态管理。
- 复用项目现有 shadcn/Base UI 组件和 Tailwind v4 原子类，不新增页面级传统 CSS。

## 非目标

- 不修改服务端 endpoint、数据库 Schema、Worker 接口或回测引擎。
- 不新增策略删除、重命名、归档接口；既有策略名称在创建后保持固定，新版本中的 `schema.name` 与策略记录名称同步。
- 不在本期实现 `all`、`any`、`not` 条件树的可视化编排器；复杂表达式继续通过高级 JSON 编辑。
- 不在本期实现策略版本 Diff、版本对比、参数扫描、批量回测或优化器。
- 本期策略编辑只支持配置一个标的，提交时写入 `universe.symbols[0]`；加载旧版本中包含多个标的的 Schema 时只保留首个标的，避免用户配置不会生效的多标的内容。
- 不新增图表库。视觉预览中的权益曲线图属于后续增强；本期结果 Dialog 复用现有指标、权益数据表和交易明细表。
- 不修改 `/strategy` 路由、主导航名称、全局主题或其他页面交互。
- 不产生订单、交易指令或自动交易行为。

## 现状与约束

- 页面入口为 `apps/desktop/src/features/strategy/StrategyDashboard.tsx`，展示组件位于 `StrategySections.tsx`，动作编排位于 `strategy.actions.ts`。
- Desktop API 已提供 `POST /backtests/strategies`、`POST /backtests/strategies/:id/versions`、`GET /backtests/strategies`、`POST /backtests/jobs`、`POST /backtests/jobs/:id/run` 和 `POST /backtests/jobs/:id/cancel`。
- `GET /backtests/strategies` 的服务端结果包含策略状态、时间和完整版本 Schema；当前 Desktop `StrategyRecord` 类型只声明了名称和版本 ID/序号，需要补齐前端内部类型。
- `strategySchemaV1` 已由 `@thesis-ledger/schemas` 导出，可用于客户端提交前校验，不应另写一套不一致的 Schema 校验器。
- 当前任务轮询规则是：存在 `queued` 或 `running` 等非终态任务时，每 1.5 秒刷新任务列表；终态全部结束后停止轮询。
- 当前行情准备通过 `/market/:symbol/bars?timeframe=1d` 获取首个标的日线；HTTP 错误回退空 bars，网络错误阻止排队，该兼容语义必须保留。
- 项目使用 Vite、React、Tailwind v4、Base UI、`base-vega` 和 `lucide`；`Tabs`、`Sheet`、`Dialog`、`Field`、`Select`、`Badge`、`Progress`、`Empty`、`Alert` 等组件已经安装。
- 所有表单使用 `FieldGroup`、`Field` 和对应 Label/Description/Error；Select item 必须位于 `SelectGroup`；overlay 必须包含可访问的 Title 和 Description。
- 样式优先通过现有原子类和组件变体组合；不得为本页面新增传统 CSS 选择器、`!important` 或视觉专用渲染分支。
- 受影响页面继续遵守文件大小和复杂度 guardrail，容器负责状态编排，局部组件负责单一交互区域。

## 设计方案

### 页面信息架构

页面头部保留“策略实验”标题和可复现性说明，右侧提供：

- 低强调“刷新”操作，用于显式重新获取策略和任务。
- 主操作“新建策略”，打开策略编辑 Sheet。

标题下使用 `Tabs` 分为：

1. “策略库”：管理策略及其最新版本，默认打开。
2. “回测任务”：查看任务状态、进度、操作和结果。

全局数据错误或陈旧状态继续使用 `DataStateBanner`。空数据不再同时显示全局“暂无数据”横幅和创建表单，而由当前 Tab 内的 `Empty` 提供上下文和下一步操作。

### 策略库

策略库采用现有安静表格样式，至少展示：

- 策略名称与首个标的/比较基准摘要。
- 最新版本 Schema 的状态；缺少时回退策略记录状态。
- 最新版本号和创建时间。
- 最近一次关联回测的中文状态；没有任务时显示“尚未回测”。
- “编辑为新版本”和“开始回测”操作。

版本按 `version` 数字排序，任何需要“最新版本”的行为都使用排序结果，不依赖接口数组顺序。策略行不能读取页面上另一个策略的编辑草稿。

空策略库显示“还没有策略”、简短说明和“创建第一条策略”按钮。加载中使用 Skeleton 或现有加载状态；错误与陈旧数据继续保留重试能力。

### 策略编辑 Sheet

新建和编辑共用右侧宽 Sheet：

- 新建模式标题为“新建策略”，提交操作为“创建策略”，成功后生成 `v1`。
- 编辑模式标题为“编辑为新版本”，明确显示“基于 vN 创建 vN+1”，提交操作为“保存为新版本”。
- 编辑模式加载所选版本 Schema 的副本；保存只创建新版本，不覆盖来源版本。
- 现有策略名称只读，并强制同步到提交 Schema 的 `name`；本期不提供策略重命名。

Sheet 内使用二级 `Tabs`：

1. “常用配置”：表单化高频字段。
2. “高级 JSON”：编辑完整 Schema，并通过显式“应用 JSON”同步回表单。

常用配置至少覆盖：

- 策略名称、描述、状态。
- `universe.symbols`、`universe.asOf` 和 `benchmark`；`universe.symbols` 使用不带默认列表的单选搜索 Combobox，已选代码直接显示在输入框中，通过标的目录按名称或代码选择一个标的；`benchmark` 使用支持按名称或代码搜索全量标的的 Combobox，打开时默认展示常用指数列表（包括科创 50 `000688.SH`），搜索结果来自已同步的标的目录，提交值仍为标的代码，未知历史代码保留原值显示。
- `entrySignals`、`exitSignals` 的新增、编辑和删除；每条信号的“指标”使用下拉枚举，提供 `close`/`price`（收盘价）、`open`（开盘价）、`high`（最高价）、`low`（最低价）和 `volume`（成交量），避免填写回测引擎无法识别的名称；高级 JSON 中的历史值仍可读取并在未修改时保留。
- `stopLoss`、可选 `takeProfit`、`sizing`。
- `execution.price`、`execution.tPlusOne`、`execution.lotSize`。
- `cost` 下的佣金、最低佣金、印花税和滑点。

`entryCondition`、`exitCondition`、`riskConstraints` 及其他表单未直接呈现的合法字段必须在常用配置编辑过程中保留，不得因表单更新被静默删除。

### 表单与 JSON 状态模型

编辑器只维护一个已解析 Schema 作为权威状态：

- 常用配置直接更新权威 Schema，并可随时生成格式化 JSON。
- 进入高级 JSON 时，从当前权威 Schema 生成 JSON 草稿。
- JSON 草稿在用户点击“应用 JSON”前不改变常用配置。
- “应用 JSON”先执行 JSON 解析，再使用 `strategySchemaV1.safeParse` 校验；通过后替换权威 Schema，失败时保留 JSON 草稿并显示路径明确的内联错误。
- 最终保存前再次执行同一 Schema 校验；失败时不关闭 Sheet、不发请求。
- 顶层策略名称和 `schema.name` 不允许分离。

字段错误使用 `Field` 的 invalid 状态、`aria-invalid` 和 `FieldError`。短暂成功使用 Toast；需要用户修正的错误保留在 Sheet 或 Dialog 内，不只依赖 Toast。

### 回测配置 Dialog

从策略行点击“开始回测”打开居中 Dialog，展示不可编辑的策略名称、版本号、首个标的和 Schema 校验状态，并提供：

- 开始日期。
- 结束日期。
- 初始资金。

校验要求：开始日期不得晚于结束日期，初始资金必须大于零，选中版本必须包含可识别的 `universe.symbols[0]`。当 Universe 包含多个标的时，Dialog 明确提示“当前回测仅使用首个标的”。

用户只看到一个主操作“开始回测”。前端内部按顺序执行：

1. 从选中版本保存的 Schema 读取首个标的并获取日线 bars。
2. 使用选中版本 ID、Dialog 参数、版本 Schema 和 bars 创建 queued job。
3. 排队成功后调用 run endpoint 启动同一任务。
4. 成功后关闭 Dialog，切换到“回测任务”Tab，并通过 Query 失效/轮询显示进度。

若排队失败，Dialog 保持打开并显示可操作错误。若排队成功但自动启动失败，任务保留为 `queued`，提示“任务已排队，可在任务列表重试运行”，不得回滚或伪装为未创建。

### 回测任务

任务表至少展示：

- 策略名称与 `vN`；无法匹配本地策略数据时回退截断版本 ID。
- 回测起止日期和初始资金；旧任务缺少字段时显示“暂无”。
- 中文状态：排队中、运行中、已完成、失败、已取消；未知值保留原始字符串作为兼容回退。
- 仅在运行中展示 `Progress`；终态不保留无意义的 100% 进度列内容。
- 创建时间。
- queued 任务的“运行”、非终态任务的“取消”、成功任务的“查看结果”。

轮询继续由 `useStrategyQueries` 管理。手动刷新是辅助操作，不替代自动轮询。

### 回测结果 Dialog

成功任务点击“查看结果”打开大尺寸居中 Dialog，Title 包含策略名称与版本号，Description 包含回测区间。结果使用二级 Tabs 分为：

- “摘要”：最终资产、累计收益、最大回撤、交易胜率和结果警告。
- “权益数据”：复用现有最近 20 个权益数据点表格。
- “交易明细”：复用现有交易表格。
- “复现信息”：引擎版本、数据时点、结果校验和、成本模型和已知偏差。

任务尚未完成时不提供“查看结果”；失败任务通过任务状态和 warnings 展示失败原因。Dialog 内容允许纵向滚动，但页面主体不因结果展开而增长。

### 组件与文件边界

实现时保持以下职责边界，具体文件名可按现有 feature 命名微调：

- `StrategyDashboard`：Query/Mutation 编排、主 Tabs、选中对象和 overlay 开关。
- 策略库组件：列表、状态映射和行操作。
- `StrategyEditorSheet`：编辑器状态、常用配置和高级 JSON。
- `BacktestSetupDialog`：参数校验与开始回测确认。
- 任务组件：任务表、状态、运行/取消入口。
- `StrategyResultDialog`：结果解析和四个结果 Tabs。
- `strategy.actions.ts`：创建策略、创建版本、排队并启动、取消/重试等异步动作。
- `strategy.api.ts`、`strategy.mutations.ts`、`strategy.types.ts`：补齐已有服务端能力的 Desktop 内部契约。

不得把全部表单和结果逻辑重新集中到单个巨型文件。

## 对外行为或接口变化

- `/strategy` 路由和导航名称保持不变。
- Desktop API 模块新增对既有 `POST /backtests/strategies/:id/versions` 的调用，不新增服务端 endpoint。
- `StrategyRecord`、版本和任务的 Desktop 内部类型补充 Schema、状态、时间、区间、input、engineVersion、resultChecksum 等实际响应字段；这是前端类型对齐，不改变 wire shape。
- “保存新版本”仅用于已有策略；首次创建按钮改为“创建策略”。
- 策略行“排队回测”改为“开始回测”，用户不再需要先排队再到任务表点击运行。
- 任务主标识从 UUID 改为“策略名称 + 版本号”，UUID 保留为兼容或诊断信息。
- 回测区间和初始资金从硬编码改为 Dialog 提交值。

## 数据、状态或兼容性影响

- 历史策略版本和历史回测记录保持不变；新版本继续通过服务端版本号递增。
- 创建新版本不修改来源版本；版本编辑器始终从所选版本复制完整 Schema。
- 策略状态展示优先读取最新版本 Schema 的 `status`，缺失时回退策略记录状态，再缺失时显示“未知”。
- 旧任务可能缺少前端新增展示字段，所有新增字段均需提供“暂无”或 ID 回退，不得导致列表渲染失败。
- bars 的 HTTP 错误回退空数组和网络错误阻止排队语义保持不变。
- Query key、轮询间隔和终态判断保持兼容；Mutation 成功后失效 `strategyKeys.root` 下相关数据。
- 页面不持久化未保存草稿；关闭有修改的 Sheet 是否二次确认沿用项目 overlay 通用约定，若实现确认行为必须在任务文档中补充测试。

## 风险与备选方案

- 表单与 JSON 双入口可能产生状态漂移。通过“已解析 Schema 单一权威状态 + 显式应用 JSON”消除隐式双向同步。
- 服务端策略名称和版本 Schema 名称可能不一致。编辑已有策略时固定父策略名称，并在提交前覆盖 `schema.name`。
- 高级字段可能被常用表单覆盖。更新字段时必须基于完整 Schema 做局部不可变更新，并测试 `entryCondition`、`exitCondition` 和 `riskConstraints` 的保留。
- queued 后自动 run 失败会形成中间状态。将 queued 视为有效任务，任务表提供重试运行，不执行补偿删除。
- 大结果放入 Dialog 可能超过可视高度。使用大尺寸但有边界的 Dialog 内容区滚动，表格继续使用已有横向滚动容器。
- overlay 和表单拆分可能扩大文件数量。以职责边界换取可测试性，并通过现有 guardrail 控制函数长度、复杂度和文件大小。
- 若一期实现成本超出预期，优先保留版本语义、精确版本回测、参数 Dialog 和任务可读性；复杂条件、图表和版本对比不得挤入本期。

## 未决问题

无。视觉预览用于确认信息架构和交互方向；本规格明确将权益曲线图、复杂条件树和版本对比留到后续增强。

## 验收标准

1. 页面默认展示“策略库”和“回测任务”Tabs，完整 JSON 不再长期占据页面主体。
2. 无策略时显示聚焦空态和“创建第一条策略”；加载、错误、陈旧和有数据状态均可区分并可重试。
3. 新建策略通过 Sheet 完成，主操作为“创建策略”并生成 `v1`；已有策略通过同一 Sheet 保存为新版本，来源版本不被覆盖。
4. 常用配置和高级 JSON 使用单一权威 Schema；无效 JSON/Schema 显示内联错误，不能提交或污染表单状态。
5. 常用配置更新不会删除未直接呈现的合法高级字段，现有策略名称与 `schema.name` 保持一致。
6. 策略库展示名称、最新版本、状态、更新时间和最近回测，所有“最新版本”计算不依赖接口数组顺序。
7. “开始回测”Dialog 允许设置有效起止日期和正数初始资金，并明确绑定策略名称与版本号。
8. bars、排队和运行均使用选中版本保存的 Schema；不得读取另一个策略或未保存编辑器草稿。
9. 排队成功后自动启动；启动失败时 queued 任务保留并可从任务列表重试。
10. 任务表以“策略名称 + vN”为主要标识，使用中文状态，运行中显示进度，保留运行、取消和查看结果操作。
11. 成功任务的结果在 Dialog 中按摘要、权益数据、交易明细和复现信息分区展示；页面主体不追加长结果区。
12. 非终态任务保持 1.5 秒自动轮询，终态全部结束后停止；手动刷新为辅助操作。
13. 页面使用现有 shadcn/Base UI 组件、Field 表单结构、原子类和 TanStack Query；不新增传统 CSS、嵌套三元或手工请求竞态状态。
14. 策略 API/动作、Schema 状态转换、精确版本回测、排队后启动失败、轮询、空态和主要 overlay 交互具有针对性测试。
15. Desktop typecheck、目标测试、build、格式检查、文件大小 guardrail 和 `git diff --check` 通过；运行时浏览器验收结果与缺口单独记录。
