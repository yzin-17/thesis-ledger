# 移除 AI 执行路由能力声明配置 Spec

> 任务标识：2026-09-21-remove-ai-capability-declaration  
> 日期：2026-09-21  
> 状态：本地实现与验证完成；Electron 实机视觉验收和真实外部 Provider 验收未执行  
> 对应任务：[实施任务](../tasks/2026-09-21-remove-ai-capability-declaration.md)  
> 修订：[AI 接入层迁移 Spec](2026-09-19-vercel-ai-sdk-integration.md)

后续范围修订（2026-09-21）：上游服务限制和免费依据随后分别由[移除 AI 执行路由上游服务限制 Spec](2026-09-21-remove-ai-upstream-restriction.md)与[移除 AI 执行路由免费依据 Spec](2026-09-21-remove-ai-free-evidence.md)移除。本 Spec 中对这两项能力的“保留”仅描述本 Spec 完成时的历史边界，不代表当前配置契约。

## 背景与问题

现有 AI 执行路由要求用户为每个“模型、生成模式、生成契约”填写能力声明来源、来源版本和声明者。该信息不会自动验证模型能力，却会增加本地 Provider 配置成本，并在缺少声明时阻断发送。对 LM Studio 等本地模型，这个门槛不能改善连接错误或输出错误。

本 Spec 将能力声明配置从用户配置和接入就绪门禁中移除，同时保留真正参与执行安全的 adapter 契约证据、Provider 健康、预算/费用授权、能力撤销和真实验收分层。上游服务限制与免费依据的后续变化见文首修订说明。

## 目标

1. Desktop 执行路由不再展示或提交能力声明来源、来源引用、来源版本和声明者。
2. 新的 AI Provider 路由契约不再要求能力声明；接入就绪不再因为缺少能力声明而阻断。
3. 已保存的旧 JSON 配置可以继续读取；旧字段被丢弃，下一次保存不再写回。
4. 连接健康、adapter 契约证据和真实业务验收继续保持独立，不互相冒充。

## 非目标

- 不移除生成模式、生成契约、adapter 契约证据或本地契约测试。
- 本 Spec 完成时不移除免费依据和费用授权门禁；后续费用授权改由用户填写的 Provider 费用负责，详见关联 Spec。
- 不移除针对明确失配组合的 `capabilityRevocations` 能力撤销机制。
- 不把连接测试改造成结构化业务验收，也不因此自动宣称真实 Provider 可用。
- 不修改数据库表结构；执行路由继续存放在现有 Provider JSON 中。

## 现状与约束

- `capabilityDeclaration` 当前同时出现在共享 Schema、Server 输入与 readiness 结果、Desktop 编辑器和相关测试中。
- `adapterEvidence` 是受控发布输入，仍是接入就绪所需的本地契约证据。
- 历史数据库设置和 `AI_PROVIDER_CONFIGS_JSON` 可能已经包含 `capabilityDeclaration`，读取兼容不能把整条路由丢弃。
- 新旧 Provider 的配置来源、凭证保护和现有路由指纹规则继续有效；移除声明字段后，指纹不再包含该字段。

## 设计方案

### 配置与契约

执行路由输入、Provider 配置和 `AiProviderModelExecution` 读模型删除 `capabilityDeclaration`。旧输入在 AI 路由解析边界只移除这个已废弃字段，再按当前严格 Schema 校验；其他未知字段仍然拒绝。新保存结果不包含该字段。

### 接入就绪

就绪判断保留配置有效、启用状态、Provider 健康、adapter 契约证据、预算授权和能力撤销等条件，删除 `capability_declaration_missing` 原因。`ready` 只要求仍然适用的本地 adapter 契约证据及其他现有条件。

### Desktop

执行路由标题和说明改为只描述路由配置与验证条件；删除能力声明下拉框及其附属输入。推理强度校验继续引用 Provider 能力配置，但不再使用“能力声明”作为用户概念。

### 兼容与清理

读取旧配置时忽略能力声明字段，不执行破坏性迁移；用户下次保存或环境配置重新加载后使用无该字段的归一化结构。能力撤销相关文案改为“能力已撤销”，避免继续暗示能力声明功能仍存在。

## 数据、状态或兼容性影响

- 无数据库 migration。
- 旧 JSON 中的能力声明不会继续进入运行快照、配置指纹或公开读模型。
- 旧 JSON 中除能力声明外的无效字段仍按既有严格校验处理；不能借兼容清理放宽其他契约。
- 能力撤销机制继续按模型、模式、契约和配置指纹生效；移除声明后使用新字段集合计算指纹，绑定旧声明字段的历史撤销记录不自动延伸到新配置。

## 测试策略

### 关键可观察行为

- 新建/编辑执行路由的输入不包含能力声明字段。
- 旧配置带有能力声明时仍能读取，归一化结果不包含该字段。
- 具备 adapter 契约证据但没有能力声明的路由可以进入 `ready`；连接健康、预算和撤销条件仍能阻断。
- Desktop 不渲染能力声明控件，Provider 编辑器现有模型、模式、费用和超时配置不受影响；后续费用字段语义由关联 Spec 定义。

### 测试层级与证据边界

共享 Schema、Server readiness/配置解析、Desktop Provider UI 及受影响策略 fixture 执行定向测试；再执行受影响包的 typecheck/build 和 `git diff --check`。这些证据证明源码和契约行为，不替代 Electron 实机视觉验收或真实外部 Provider 验收。

## 风险与备选方案

风险是旧配置若未在读取边界清理会被严格 Schema 丢弃。通过单一的旧字段归一化入口和数据库/环境两类回归测试控制该风险。若未来需要审计能力来源，应另建独立的验证记录或目录能力，不恢复为每条本地路由的手工必填门槛。

## 未决问题

无。

## 验收标准

- AC1：Desktop 执行路由编辑器不再显示能力声明来源及其附属输入，且保存请求不再提交相关字段。
- AC2：共享输入/输出契约不再要求或返回 `capabilityDeclaration`；旧数据库与环境 JSON 读取时兼容丢弃该字段。
- AC3：没有能力声明但满足其余现有条件的路由可以被 Server 判定为 `ready`；`adapterEvidence`、健康、预算和撤销门禁仍有效。
- AC4：能力声明缺失错误码、相关校验和过时用户文案被移除；能力撤销和推理能力校验文案仍准确。
- AC5：受影响的共享 Schema、Server、Desktop 定向测试、typecheck/build 和差异检查通过；未声称浏览器/Electron 或真实 Provider 验收通过。
