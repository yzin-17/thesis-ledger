## 背景与目标

将 AI Provider 配置收敛为两层事实：Provider 负责连接，Provider 下的模型负责费用与业务用途。用户通过模型配置研究报告、参数优化和策略发现用途，服务端继续以现有 `executionRoutes`、契约版本、预算和冻结快照作为执行事实源。

本 Spec 是对上传设计稿的仓库内实施索引，不替代上传文件中的完整交互、兼容迁移、真实运行态和验收细节。实施必须保留当前工作树中已经移除的能力声明、免费依据和上游限制，不得重新引入。

## 本轮实施边界

第一阶段建立可复用的模型级价格与用途投影：

- 价格归属于 `Provider + Model`，缺失值保持未知，显式零值保持为零；旧 Provider 级价格只用于兼容读取和显式迁移。
- 业务用途映射到现有路由契约；同一 Provider、模型、用途只允许一条活跃路由，输出模式不再构成用户侧重复配置键。
- Desktop 在现有 Provider 编辑器中按模型展示价格和用途配置，目录获取只更新候选模型，不覆盖已有价格或用途。

本轮已追加双页签连接界面、显式认证模式、指定模型最小生成测试、业务用途测试、测试历史和研究默认的实现：连接配置与模型用途在同一编辑器中分栏展示，`authMode` 进入保存、目录和生成请求，无需认证模式不会读取或发送历史 / 环境 Key；业务用途测试绑定目标模型、用途、输出方式和实际契约；保存测试保留用量、上游费用或配置估算，未知费用不补零；测试支持请求级取消，取消写入历史但不把 Provider 健康状态降级；研究创建读取并冻结显式默认及其修订号，不再按列表顺序猜测。兼容迁移 dry-run、版本保护和默认引用原子变更也已形成服务端实现与局部测试。真实运行态验收仍属于独立门禁，不能被本地测试替代。

## 稳定契约

业务用途及对应契约：

| 用户文案 | 内部契约 ID |
| --- | --- |
| 研究报告 | `research` |
| 参数优化 | `parameter_optimization` |
| 策略发现 | `strategy_discovery` |

模型价格输入使用可选字段表达未知：`costPer1kInput`、`costPer1kOutput`、`costCurrency`。服务端维护 `pricingVersion`、更新时间和来源；客户端不得提交服务端生成的价格版本作为事实。

兼容读取必须满足：旧配置仍可读取；保存新配置时已有模型级价格不被旧 Provider 价格覆盖；新增模型价格默认未知；历史任务和历史费用不被当前价格重算。

测试生命周期契约：每次实际 Provider 测试携带 UUID `requestId`；服务端只允许同一请求单飞，取消通过 `POST /ai/providers/:name/test/cancel` 触发；取消结果为 `cancelled`，已知 usage 保留，外部费用和未知 usage 保持 unknown，不自动重试。保存 Provider 的测试历史复用 `ProviderHealthCheck.details`，取消只写历史，不更新当前 Provider 健康状态。

兼容迁移契约：`POST /ai/providers/migration/dry-run` 只读生成逐 Provider 报告；完整旧价格、零值和已有模型级价格必须保留，缺字段、重复用途路由和无法安全转换的值报告为冲突，不静默补零、合并或覆盖。已有 Provider 的保存、启停和删除使用 `expectedRevision` 条件更新；涉及研究默认时同时校验设置修订并在同一事务内清除引用。

### 配置与默认引用的持久化边界（2026-10-04）

默认候选检查与默认设置提交、Provider 保存中的默认保留检查、Provider 启停/删除中的默认确认和清除，必须共享同一 PostgreSQL 事务临界区，包括尚无 `global` 默认记录的首次设置。当前实现由 AI 拥有的配置事务边界统一使用事务级 advisory lock；通用 Provider 存储只接受可选事务客户端，不依赖 AI 编排。临界区仅包含配置读取与写入，模型验证在外部完成，成功记录与保存 CAS 冲突的审计仍独立持久化。

停用的研究用途不能作为默认候选；普通保存不能停用默认 Provider 或移除其默认模型/用途，必须先走现有默认变更或显式生命周期确认。已删除 Provider 的过期草稿不能通过带旧 `expectedRevision` 的保存重新创建。这里只补强既有并发和失效保护，不改变研究任务提交/冻结的验收责任。

研究提交的默认读取、客户端设置修订校验、路由/价格冻结和 AiRun 创建必须共同处于上述配置事务临界区。创建先进入时，默认切换等待该创建提交，旧任务保持已冻结的 Provider/Model/价格和设置修订；默认切换先提交时，旧修订的新研究请求返回冲突且不创建任务。该临界区只覆盖入队记录，不包含模型调用或执行器运行。

超时契约：Provider 的 `timeoutMs` 用于目录获取和非流式连接探针的单次总超时，留空时继承系统默认；它不截断持续产生输出的流式用途验证、研究生成或策略优化生成。流式请求的首次输出与输出间隔分别按“用途覆盖 → Provider 默认 → 系统默认”解析。用途验证仍受本次操作的总期限、调用次数和 Token 上限约束；研究与策略生成分别受冻结任务期限和实验剩余请求期限约束。持续输出不能越过这些绝对期限，停顿超时与绝对期限超时也不能冒充用户取消。界面须说明各字段的适用请求和生效来源。

## 验收标准

- AC-01：模型级价格可独立保存、读取和展示；同一 Provider 的不同模型可以有不同价格。
- AC-02：双零费率、非零费率、缺失价格和单边零费率保持可区分，空值不得转换为零。
- AC-03：旧 Provider 级价格可兼容读取并按既有模型迁移；新增模型不隐式继承旧全局价格。
- AC-04：同一 Provider、模型、用途不能保存两条不同输出模式的活跃路由；旧冲突不得静默选择。
- AC-05：模型编辑器可以勾选用途并映射到既有路由；目录刷新不自动选用途、改价格或删除已选模型。
- AC-05a：用户主动移除模型时，父级 Draft 同步移除该模型的全部用途路由（含停用用途）、价格、默认生成方式和推理元数据；其余模型的配置保持原值。删除最后一个模型仍提示至少配置一个模型；研究默认引用继续由既有保存保护校验，不隐式改选其他模型。
- AC-06：已有能力声明、免费依据和上游限制仍保持移除状态。

## 通用模型请求参数（G3接续）

模型默认配置可选保存 requestOptions：body 为用户填写的额外 JSON 请求参数；headers 为生成请求的额外非认证头；outputTokenLimit 可为 budget 或 upstream。旧配置省略时保留原行为；编辑已有配置时省略该字段保留原参数，显式空对象清除参数。持久化中存在非法参数时阻断该Provider，不把它丢弃后继续执行。前端由用户按模型文档填写并通过父级表单显式保存，不按 Provider 名称、域名或模型 ID 自动注入供应商字段。

额外参数只对生成请求生效，不改变目录、认证或目标地址；body按顶层键覆盖同名非受保护参数，嵌套值整体保留，不做深度合并或 null 删除。模型、messages／instructions／input、stream、输出格式、工具、单次结果数、token 上限及认证／重试／期限等由现有合同拥有的字段不能通过 body 覆盖。拒绝原型污染键和凭据字段；额外参数只接受有限、可序列化且有界的 JSON 对象。headers只接受合法HTTP头名和无控制字符的有限字符串，不允许认证、cookie、密钥／token头或Host、Content-Type、Content-Length及连接控制头；与参数共同冻结并在变换后取证。需要网关日志时由用户显式填写相应非认证头，不在Server内识别供应商自动添加。

upstream 表示实际请求不发送 max_tokens、max_completion_tokens 或 max_output_tokens；任务内部预留／结算预算继续存在。该选项仅对已明确配置输入、输出零价格和有效币种的模型就绪，不以用户同意预算代替零价前提；Anthropic Messages 的必填输出上限不支持该选项。未知和非零价格继续使用原预算上限或阻断，不扩大费用边界。

参数进入配置指纹、用途验证指纹、研究冻结路由及实际 SDK 输入；任何参数变化使旧验证失效，在途研究不能悄悄改用新参数。所有实际 HTTP 参数在通用传输变换之后进入诊断和 trace；配置参数不是秘密存储，不允许填入凭据。正式验收不得用私有 httpClient 注入代替通用配置。

- AC-31：旧配置省略 requestOptions 时行为不变；新增配置保存、读取和模型移除过滤完整，不需要数据库结构迁移。
- AC-32：共享输入、Server 与前端一致校验通用参数，保护系统拥有字段、凭据及原型键，坏草稿不能静默保存旧值。
- AC-33：参数变化使就绪／用途验证指纹失效，冻结研究明确保存并匹配参数；普通模型无供应商字段注入。
- AC-34：真实 SDK 出站通过通用配置传递嵌套参数；upstream 下没有 token 上限字段，内部预算保留，非零／未知价格及不支持协议被阻断；trace 记录变换后的实际正文。
- AC-35：前端可编辑、错误恢复、保存、重开回显并保留其他默认配置及原用途合同版本；研究用途可显式选择V1／V2，不因普通编辑降级合同。正式 G3 独立核对实际路由、报告／引用／历史及 trace，完成后按授权恢复配置和开关，保留验收报告。

- AC-36：研究V2用途探针提供经原Zod校验的最小合法格式实例，包含JSON Schema无法完整表达的动作／引用规则；父级测试并保存和已保存用途测试均向实际探针传递所选准确合同版本，不回退到默认 V1。不修补模型输出或放宽业务校验。该探针只验证所选合同的生成能力，正式材料、数值和来源绑定仍须独立G3验收。

## 模型用途交互收敛（2026-09-22）

本次依据“模型业务用途配置交互优化”草稿补充以下稳定交互和保存语义：

- 同一模型可启用多个业务用途；点击未启用用途会启用并设为当前编辑用途，点击已启用用途只切换当前编辑用途，不执行取消。
- 同一模型同时只显示一个当前用途详情面板；取消用途只能在该面板中进行。取消当前用途后，前端优先选择原位置的下一个用途，再回退到上一个用途；没有剩余用途时不显示详情面板。
- `modelDefaults[model].mode` 保存模型默认输出方式；每条执行路由保留运行时有效 `mode`，并以可选 `modeOverridden` 标识其是否为显式用途覆盖。修改默认方式只更新未覆盖用途的有效值，不覆盖显式覆盖。
- 旧配置不含 `modelDefaults` 或 `modeOverridden` 时兼容读取：既有路由按显式覆盖处理，避免首次编辑或保存静默改写原有输出方式。
- 模型测试和用途测试仍是独立动作；用途测试只从当前详情面板的路由读取模型、用途和有效输出方式，不改变启用状态。

新增局部验收：

- AC-07：多用途启用、当前编辑用途和取消动作严格分离，任意时刻每模型最多一个详情面板。
- AC-08：模型默认输出方式和用途显式覆盖可分别保存、回读；修改默认方式不会改写显式覆盖。
- AC-09：旧执行路由没有新标记时保持既有有效输出方式，不因兼容读取产生静默重写。

### 用途配置显式保存与停用保留（2026-09-22）

本节取代本文件较早版本中“用途 Chip / 更多菜单取消用途”的交互描述；路由、预算与运行时架构不作其他调整。

- `executionRoutes` 新增可选 `enabled?: boolean`。缺少字段的历史记录等价于 `enabled: true`；本次不引入数据迁移。
- 停用用途只保存 `enabled: false`，不得删除同一模型、用途的路由记录；输出方式和两个超时覆盖值继续保留。再次启用改回 `enabled: true` 并复用该记录。

- 宽屏下模型用途使用左侧“配置对象 / 模型默认”与右侧当前用途配置的两列布局；窄屏自然堆叠，不新增嵌套 Card。

新增局部验收：

- AC-12：历史 route 缺少 `enabled` 时仍可执行；`enabled: false` route 可回读但不会进入业务执行候选集。
- AC-13：同一模型的用途参数可先修改、测试，再由父级表单一次写入；失败时父级 Draft 保留，取消统一还原所有 Provider 配置。
