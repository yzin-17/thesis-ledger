# 策略生成模块重设计方案

2026-11-18 起草，2026-11-19 完成设计评审。建议只为已有日线策略的单笔委托有效期修改做离线试点。正式三入口继续使用 v5。随后完成的[离线试点](../evidence/2026-11-19-strategy-authoring-order-validity-pilot.md)验证了两个方向，[真实模型对照](../evidence/2026-11-19-strategy-authoring-order-validity-model-recheck.md)已取得两份首次成功、隔离保存和冻结回放回执。当前有效合同及验收状态分别由[交易计划规格](../specs/2026-11-15-backtest-trade-plans.md)和[实施任务](../archive/tasks/2026-11-15-backtest-trade-plans.md)维护。

## 评审结论与依据

**值得做一个局部修改的离线试点，当前保留正式 v5。** 若要把一张买单从当天有效改为两根有效，已有基线足以确定其余策略内容。让模型只给出订单 ID 和新期限，服务端可以逐字段证明其他委托原样保留。发现和从零编写缺少这份完整基线，模型仍需选择交易规则。两者继续沿用各自入口，暂缓共用转换层。

**当前基线是 T04d.6b 累计 24／24，发现、编写、修改各 8／8。** 复用早期 11 份，后来补齐 13 份，24 份原始成功输出均经最终正式入口重放。补验的 13 个位置有 7 个首次通过，共 22 次业务生成及 8 次独立格式探针；其中局部修改只剩 `two-bars` 一个位置，首次即通过。已有证据支持 v5 完成本轮需求，也说明比较新接口时应看首次语义正确率及每次成本。24／24 记录的是分批累计覆盖。[最终实测矩阵](../evidence/2026-11-18-backtest-whole-order-and-native-recheck.md#最终实测矩阵) · [目标双容器验收](../evidence/2026-11-18-backtest-daily-order-target.md)

三个 v5 是模型用途的输出合同，当前回执中保存的策略为 `schemaVersion: "3"`。新方案仍以完整 `BacktestStrategy` 作为预览、保存和执行依据。若日后让真实模型改为返回变更，需要单独识别输出合同并验证用途资格。[用途合同](../../packages/schemas/src/ai-execution.ts) · [策略定义](../../packages/schemas/src/backtest-strategy.ts)

| 实际观察 | 设计含义 |
| --- | --- |
| 早期累计 11／24 时，发现 0／8、编写 4／8、修改 7／8。发现曾在解释中说只在空仓入场，实际却生成 EMA 交叉。有样本把模拟执行价 9 理解成 9%。 | 即使结构合法的配置也可能偏离意图。入场条件、价格及单位必须分别表达，单靠格式校验不能证明理解正确。 |
| 修改 `day` 只把买单从两根改为当天并通过。早期反向的 `two-bars` 同时改了买单和普通退出单，结构合法、业务判错；最终 v5 回执中只有买单改为两根，退出单为 DAY，止损仍为持仓期有效。复核两份操作快照，提交的范围均为整个 `execution`，基线均有独立的 `buy`、`exit` 和 `stop`。 | 现有范围能防止改动其他章节，却不能证明模型选对了章节内的订单。局部修改收益最大的是让模型少写未变内容，同时保留可核对的具体差异。 |

## 现有局部修改入口要保留什么

| 环节 | 现有行为 | 改为只返回变更后的责任 |
| --- | --- | --- |
| 提交与生成 | 提交时核对草稿修订，操作持有草稿内容、意图和选定章节。操作 Schema 把其他根字段冻结为常量或固定元组，模型仍返回完整定义。 | 继续绑定提交时的修订。可以从响应 Schema 移走范围外策略内容，只向模型提供辨认候选订单所需的 ID、动作、关联和现值。字段级选择只有在调用者明确提供时才能作为额外授权。 |
| 确认意图、范围和需求覆盖 | `validateAuthoringModification` 检查完整定义，屏蔽获准改动的章节再与基线深比较，拒绝越界与空改。固定止损已有专门的单值检查。`execution` 按整章授权，差异记录这一章的前后 JSON。 | 只接收一种业务操作，对冻结副本按唯一 ID 替换整块有效期，重新计算实际差异。模型仍可能选错同章内的单；按 ID 展示实际前后值，保留人工确认。组装后的提案仍要校验确认值、需求 ID 与真实定义路径。 |
| 提案、应用和保存 | 创建提案与确认应用均重新校验操作输出。应用时锁草稿、核对修订，重复应用已有幂等处理。保存还核对用户审核过的定义指纹。 | 将短输出转换为现有完整提案后复用这些检查。服务端生成提案只作用于基线副本，用户确认后才写草稿。生成、预览、应用须用同一基线和转换版本，审计能从原始变更重现完整定义。 |

依据为[操作提交](../../apps/server/src/strategy-authoring/authoring-operation.repository.ts)、[操作 Schema](../../packages/schemas/src/strategy-authoring-operation-schema.ts)、[修改范围与差异](../../apps/server/src/strategy-authoring/authoring-modification.ts)、[需求覆盖](../../apps/server/src/strategy-authoring/authoring-semantics.ts)、[提案确认](../../apps/server/src/strategy-authoring/authoring-proposal.service.ts)与[保存校验](../../apps/server/src/strategy-authoring/authoring-save.service.ts)。

**新增成本集中在生成与提案之间。** 服务端要解释变更、解析目标、维护旧操作与新操作的读取方式，还要对转换出的完整定义执行原生可编辑委托的顺序检查。若扩展到改名、删除、跨单联动或多项变更，还会引入父单引用、冲突顺序与整组应用问题。首个试点只接收一张现有买单的一次期限替换；这些额外操作留到有独立需求时再评估。若当前目标只是让用户看到多改了哪张单，直接细化 v5 提案的差异展示也能做到，代价更低。

## 三个入口的适用边界

| 入口 | 请求前已有的事实 | 推荐的模型工作与程序责任 |
| --- | --- | --- |
| 策略发现 | 实验范围、种子来源、周期、成本、探索目标和已有候选反馈 | 模型提出可变的信号、仓位、退出及委托规则。保留在开放目标下选择指标的能力。指定规则的受控样本单独检验。复用发现装配，在正式候选入口检查来源、可见范围、表达式深度及执行资格。 |
| 完整编写 | 原文和已理解需求、已确认标的、周期、仓位、风险、执行和费用。日线执行可能只确认了模式，也可能已确认整组订单 | 整组已确认时原样采用。仅确认模式时，模型仍要决定订单行为。用需求 ID 关联实际生成的定义路径，继续检查覆盖、来源和确认值。中文预览从最终配置生成。 |
| 局部修改 | 基线定义、草稿修订、当前意图和选定章节。对本次委托样本，系统事先只知道章节 | 模型按基线中的稳定订单 ID 和业务字段提出变更。程序在该版本副本上一次应用，计算实际差异，复用已有提案、应用与保存流程。有明确订单／字段选择时可以进一步锁定。只有章节选择时，模型给出的目标仍是待核对的建议。 |

若以后有重复且已验证的转换，再评估三个入口共享的部分。Schema 及领域合法组合沿用 `packages/schemas`。无副作用的组装和变更应用可由 `packages/domain` 持有。实验、编写各自拥有权限、确认、预算和操作生命周期。模型适配层只做传输与解析，撮合、费用和部分成交仍由原引擎负责。普通编辑器直接提供明确选择时可以复用同一转换，无需模型调用，也不能据此计入模型验收。[发现装配](../../apps/server/src/strategy-optimization/strategy-optimization-discovery.ts) · [编写操作投影](../../packages/schemas/src/strategy-authoring-operation-schema.ts) · [修改范围](../../apps/server/src/strategy-authoring/authoring-modification.ts) · [已有委托编辑](../../packages/domain/src/strategy-order-editor.ts)

**现有 v5 也能先采用其中一部分。** 对模型返回的完整定义，按订单 ID 对比基线，显示实际改了哪些单、哪些字段。如果调用者已明确选到字段，就在现有操作投影中冻结范围外的值，返回后再次核对。只有章节的旧请求继续按章节授权。整个过程使用原始完整响应，越界直接拒绝，不能将多改的字段还原后算成功。这一步能改善可核对性，但无法凭空获得 `two-bars` 所缺的字段级选择。

## 局部变更示例及将来可能的扩展

**发现与从零编写的备选设计，留待独立评审。** 模型明确选择入场条件、普通退出、买单方式及其有效期、保护的触发依据与时点、保护哪次买入、何种成交才能激活，以及平仓后等待多久。已有来源、价格表达式、持仓比例和条件树继续复用。仅新增能消除重复决策的表达，例如“无普通退出”与“使用以下退出条件”。收盘规则与盘中保护可以分别声明。只有用户同时要求时才同时生成。未说明、明确无、已有确认值必须能区分。编写时影响成交且无法唯一解释的缺项进入已有问题／审核流程。自由发现可以在实验允许的范围内提出明确假设。

在日线委托输出中，将“有无附属保护”设为显式选择。选择触价保护时，该分支必须给出价格、父买单、激活和期限，转换后必有对应保护单。模型若把“需要保护”选成“无”，这是可定位的意图误选，仍算失败。程序不会因为输出少了一张单就自行添加止损。

以下是首批日线计划中可以唯一确定的转换。

| 模型或已确认输入给出的交易选择 | 程序可唯一确定的结果 |
| --- | --- |
| 没有普通退出信号 | 生成恒假普通退出条件及合同必需的普通退出模板，采用约定的市价、DAY。该模板不会自行发单。有普通退出规则时保留其独立订单方式及期限。 |
| 以信号日最低价限价买入 | 复用同标的同周期的已声明 `low` 表达式，使用原引擎在下单时冻结的价格。市价选择无需价格字段。缺少可用来源或坐标时拒绝。 |
| 建仓每次成交后，在本次模拟执行价 9 触价卖出，保护到持仓结束 | 生成关联该建仓模板的 `stopMarket`、固定价格 `"9"`、`eachFill` 与持仓期有效。改成全成才保护时只改变相应激活语义。单条保护没有退出组。只有显式关联的止损、止盈才生成同组，按现有同父单、同激活方式校验。 |
| 收盘比首笔成交价低 10%，后续可交易开盘离场，仅作收盘保护 | 生成 `tradePlan.initialStop` 的比例 `"0.1"` 及立即启用。此选择不会产生盘中触价单。模拟坐标下的固定价格、实际报价和相对首笔成交价的比例各自保留单位及锚点。 |

**修改策略。** 例如基线中建仓单 ID 为 `buy`，模型可提出下面这一项业务变更。这里给出的是候选传输格式，ID 来自本次基线，没有固定第几张、固定订单名或任意路径写入能力。

```json
{"templateId":"buy","change":"validity","value":{"kind":"bars","bars":2}}
```

程序查找唯一目标，只更新该单的有效期。相同原则可用于改变某张保护单的父单激活方式。多项变更必须逐项列出，整体通过才产生提案。跨越选定章节、对同一值做冲突修改、引用失效或需要连带变更却未声明时均拒绝。预览显示“建仓单从当天改为两根，普通退出单仍为当天”。如果模型在只选章节的请求里另提了修改退出单，这仍可能是合法结构。系统要把第二处改动展示出来，验收按原始意图判错。

11 月 18 日的设计记录已有一个内存对照。在 `schema-modification` 的 `day-input.json` 和 `two-bars-input.json` 中分别读取真实基线，在其副本上按 ID 对 `buy` 应用**人工构造**的 DAY 或两根有效期，再用 `strategySchema.safeParse` 校验完整定义。两份都通过，两份完整 `execution` 都与各自验收预期深相等，其余章节与基线相同。原始模型实际改动的 ID 分别为 `[buy]`、`[buy, exit]`。这证明现有保存结构能承载单字段改动，模型能否从同一句自然语言选对这一项仍须实测。[真实批次位置与结果](../evidence/2026-11-18-backtest-daily-order-remaining-matrix.md#最终矩阵与检查点)

完整表达式原样使用现有类型。试点入口在发出请求前按冻结的操作类型、执行模式或明确的试点选择决定。普通发现没有已选日线计划时保留其完整探索空间，未覆盖的高级策略走现有完整合同。失败响应不自动触发第二次生成。不解析 `intentCheck`、`reason` 或自然语言来补保护，也不从测试用例名、预期配置或样例编号决定模板。

## 校验、兼容与回退

1. **接收模型输出。** 原生 Schema 限制字段、枚举、数值、单位和目标标识，正式 `generationOutput` 在应用内再次校验。针对实际出站 Schema 验证 Draft-7 及离线 grammar。目标 LM Studio 的可生成性仍需真实回执。输入预算包含消息与实际响应 Schema，全程维持现有模型、参数、额度和时限，一次业务生成只发一次模型请求。
2. **生成可执行定义。** 在内存中对冻结事实或基线副本进行确定性转换，同一版本、同一输入产生相同的 ID、引用和定义。最终对完整定义做根校验、来源／价格坐标、阶段／父买单、保护类型与激活、退出组和修改范围校验。新建及可编辑的新订单必须 `entry, exit, …`。范围外历史数组（含 `entry, stopLoss, exit`）按原值及顺序保留。修改旧顺序且涉及委托数组时，若无法满足可编辑顺序和已授权差异，明确拒绝，不能静默重排。现有顺序检查沿原生输出投影定位数组，新格式必须在生成出的定义上显式复用同一生成规则，避免小响应绕过检查。[原生入口](../../apps/server/src/ai/ai-native-strategy-schema.ts) · [顺序检查](../../apps/server/src/ai/ai-generation-order-validation.ts) · [完整委托约束](../../packages/schemas/src/backtest-daily-orders.ts)
3. **应用及回放。** 沿用草稿修订冲突检查、幂等和保存前定义指纹。过期提案不能盖过后续编辑。校验失败保留基线。冻结、回放和中文回读只消费已保存的同一份配置。原型不增加数据库表或第二份可执行策略。试点如需撤回，只停止对新操作选择试点合同，已冻结的操作维持其原身份，已保存定义继续按原执行合同读取。[提案应用](../../apps/server/src/strategy-authoring/authoring-proposal.service.ts) · [保存校验](../../apps/server/src/strategy-authoring/authoring-save.service.ts)

## 建议的试点与取舍标准

1. **先用两份真实基线比较。** 选已有局部修改入口的 `day` 和 `two-bars`，覆盖买单从两根改为当天、从当天改为两根。使用已有 v5 正反例和最终通过回执。离线输入为同一冻结基线、原意图、原章节选择和人工构造的短响应；期望配置只用于结果断言。输入范围不靠验收场景名或预期目标缩窄。
2. **先证明服务端能忠实应用变更。** 两个方向生成的完整定义须与已验收配置深度一致。退出单、保护单及其余章节逐项不变；未知 ID、选错订单角色、无实际变化和过期修订各有明确结果。保留完整业务校验、范围外历史顺序、可核对的实际差异。比较完整请求（含 Schema）与输出的序列化字节，并记录需要新增或重复维护的业务判断。该步骤只能验证转换正确性和字节差异。
3. **决定是否进入正式入口小试。** 离线对照若仍需服务端从文字猜目标、靠默认值补交易规则，或不得不复制一套提案校验，就停止试点，保留 v5。若正确性等价且减少的重复内容值得维护这一个操作，再单独授权目标模型对照。固定同样的基线、自然语言、章节范围、模型与额度，比首次选对订单和期限、额外变更数、实际输入／输出 tokens 与耗时；探针单列。仅当两向意图、确认保存及冻结回放都通过，且有可观察的成本或可靠性收益，再考虑上线这个操作。两个样本的结果只支持这一用途。
