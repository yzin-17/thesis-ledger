## 判断

现有超额主要由完整输出 Schema、消息 JSON 转义、交易计划能力字典和业务说明累积造成。原生模式已通过结构化输出参数传递完整 Schema，消息内重复这一份不是协议或现有预检的要求。详细拆分和纯离线对照由证据文档持有。

推荐先按实际模式去重，保留全部业务能力、结构约束和需求说明，不从削减能力或按本次意图裁剪 Schema 入手。无需为本次问题调整 ATR 示例、重开其失败样本，或添加更多提示。

## 建议实施边界

1. 在发现调用链中先取得现有路由的冻结执行快照，再将其实际 `mode` 传入消息装配；同一快照用于预算、缓存身份和 SDK 执行。只调整读取与装配顺序，不更换路由或重新准入 Provider。
2. `native_schema` 消息保留合同引用、JSON 返回要求、能力含义、本次目标及历史反馈，去掉完整 `OUTPUT_JSON_SCHEMA` 文本副本。原生参数继续使用当前 `nativeStrategySchema` 的完整投影及最终 Zod 校验。内存对照已表明无需删业务说明即可回到原门槛之内。
3. `json_validated` 保留完整文本 Schema 及 `assertGenerationSchemaPrompt`；其他已有模式保持各自原要求。将“SDK 合同”与“实际生成模式”分开表达，避免用同一个布尔开关决定二者。此次先处理发现入口；编写／修改的操作投影和真实路由保持原值。
4. 输入预算估算计入原生参数中的 Schema，复用现有保守估算方式；不把消息去重误当作输出合同不再消耗输入。沿用现有缓存／提示身份失效机制，不复用旧消息的生成结果；不提高任何实际额度或期限。
5. 定向验证按模式分工：原生发现消息仍必须低于 16,000；完整结构断言直接验证原生参数；文本模式继续验证消息中完整 Schema 和预检。受控请求核对完整 `response_format`、用户目标、合同引用、模型参数及预算输入，保留原失败记录。文本模式当前超额须继续显式记录，不能删门禁或扩大阈值；若其也要满足同一完整消息上限，再单独研究等价投影及重复说明去重。
6. 上述定向检查通过后，回到 T04d 新委托的原生模型成对验收，分别验证配置、原样保存、执行／回放和中文；直接复用输入未变化的旧证据，不重跑 ATR 样本或整套无关验收。实际理解效果在这一步判定，不能由离线序列化结果推出。

## 门槛的适用范围

原固定测试只提供 `useSdkContract`，没有标明实际模式。Spec 和测试现已分别标明模式：原生消息保持 16,000，完整结构在原生参数中检查；文本校验的完整消息仍按同一数值检查，当前仍失败，不用原生通过替代。

实际模型、双端页面及目标集成验收分别由 Task 持有，不由消息定向检查推断完成。原生去重只应用于发现装配，编写／修改的消息与操作投影保持原值；历史已完成或结果未知的步骤仍遵守原幂等边界，不因本次变更重发。
